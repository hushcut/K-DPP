# R1 전달: 계산 입력 거절 시 앱 저장 중단 요청

- 작성일: 2026-10-20 (Asia/Seoul)
- 전달 대상: 준원님 — 프론트 담당 공유 및 연동 확인 요청
- 수정 영역: 프론트 담당 브랜치의 저장 분기·안내 문구·관련 테스트
- 확인 기준: `ai-integration` 로컬 `16ed3c5`, 통합한 develop `24c2409`(PR #94까지). 이 기준에서 FRONTEND/BACKEND는 develop 원본과 일치합니다.
- 문서 상태: 현재 소스를 읽어 확인한 수정 요청입니다. 이번 문서 작성에서 코드를 수정하거나 새 실기기/API 재현을 실행하지 않았습니다.

## 전달 요지

준원님, 최신 develop을 통합한 뒤 확인했는데, 탄소 계산 API가 입력을 400/422로 거절해도 앱은 임시 탄소값으로 옷장 저장을 계속하고 있습니다. 기존 AI 연동 협의안 R1의 프론트 수정이 아직 필요한 상태입니다.

백엔드 회신에서는 서버의 계산 거절·이력 미저장을 이미 검증했다고 알려 주셨습니다. 이번 요청의 핵심은 프론트가 그 거절 응답을 받은 뒤 저장을 중단하고, 입력 수정이 가능한 상태로 돌아오게 하는 것입니다. 저장 분기와 안내 문구, 저장 버튼 로딩 복구를 함께 확인 부탁드립니다.

## 1. 문제와 영향

계산할 수 없는 입력이 앱에서 저장 완료로 처리돼, 근거가 없는 임시 탄소값이 옷장·리포트·집계에 사용될 수 있습니다.

예를 들어 다음 흐름입니다.

1. AI가 아세테이트(`acetate`) 100%를 인식합니다. 소재 인식 성공과 탄소 계산 지원 여부는 별개입니다.
2. 해당 소재의 계산 기준이 없으면 `POST /api/carbon/calculate`가 400 `MATERIAL_NOT_FOUND`와 `detail.unknown_materials`로 거절합니다.
3. 프론트는 400/422를 `CarbonApiErrorType.badRequest`로 분류합니다.
4. `_submitClothes()`는 인증 오류만 별도로 종료하고, 다른 계산 오류는 `fallbackMessage`를 설정한 뒤 `addClothesForOwner()`로 진행합니다.
5. 서버 계산 전 만든 로컬 초안이 저장됩니다. 등록되지 않은 소재의 로컬 기본 배출계수는 10.0이며, 안내 문구도 “기준이 없어 임시 추정값으로 저장했어요”입니다.

이는 소스에서 확인한 흐름이며, 새 사진이나 운영 서버로 이번에 실측한 재현 기록은 아닙니다. 서버의 계산 이력 미저장과 앱 옷장의 저장 중단은 각각 확인해야 합니다.

## 3. 요청하는 최소 수정

대상은 **탄소 계산 API의 400/422 입력 거절**입니다. 스캔 API의 422 소재 추출 실패와 구분해 주세요.

1. `badRequest`이면 옷장 추가·저장 완료 콜백·리포트 전환으로 진행하지 않습니다.
2. 입력한 소재·비율과 폼을 유지해 수정하거나 재촬영할 수 있게 합니다. 미지원 소재를 임의로 다른 소재로 바꾸거나 계수를 추가하지 않습니다.
3. 저장하지 않았으므로 “저장했어요” 문구를 사용하지 않습니다. 예: “소재와 혼용률을 확인해 주세요”, “이 소재는 탄소 계산 기준이 없어 저장할 수 없습니다.”
4. 거절 경로에서도 저장 버튼의 로딩을 해제하고 재시도할 수 있게 합니다.
5. 정상 계산 성공과 기존 직접 입력 저장 동작을 함께 확인합니다.

**로딩 복구 주의:** 현재 `_isSaving` 해제는 옷장 저장 구간의 `finally`에 있습니다. 계산 오류 처리에 `return`만 추가하면 그 구간에 도달하지 않아 버튼이 계속 잠길 수 있습니다. 조기 종료 분기에서 복구하거나 전체 저장 흐름의 종료 처리를 조정해 주세요.

네트워크·시간 초과·서버 장애·401 인증 만료·비로그인 저장 정책은 별도입니다. 이번 R1 때문에 모든 오류의 저장 정책을 한꺼번에 바꾸지는 않는 최소 범위입니다.

## 4. 확인할 시험

서버 응답을 모의하는 위젯 테스트로 먼저 확인할 수 있습니다. 새 Vision 호출이나 실제 의류 사진은 필수적이지 않습니다.

| 시나리오 | 기대 결과 |
| --- | --- |
| 계산 400 `MATERIAL_NOT_FOUND` | 옷장 추가 0회, 저장 완료 콜백 0회, 입력·소재명 유지, 계산 불가 안내 |
| 계산 400 — 비율 등 다른 입력 거절 | 저장하지 않고 수정 가능, 저장 완료 화면·문구 없음 |
| 계산 422 `VALIDATION_ERROR` | 저장하지 않음, 입력 유지, 로딩 해제 |
| 거절 후 입력을 고쳐 다시 저장 | 저장 버튼 재사용 가능, 새 입력으로 계산 재요청, 성공 시 1회 저장 |
| 정상 계산 200 | 서버 계산값·저장 ID를 사용해 정상 저장, 불필요한 중복 저장 없음 |
| 401·네트워크·시간 초과·서버 오류·비로그인 | R1 입력 거절과 혼동하지 않고 기존 정책 범위를 확인 |

프론트의 기존 [scan_screen_test.dart](../../../FRONTEND/test/scan_screen_test.dart#L501)는 서버 오류(`CarbonApiErrorType.server`)일 때 임시 저장하는 동작을 검사합니다. 이 검사는 400/422 입력 거절의 저장 중단을 검증하는 시험이 아니므로, 해당 전용 시나리오가 필요합니다.

이번 통합 후 Flutter 3.41.5 / Dart 3.11.3에서 분석 및 기존 테스트 689개가 통과했습니다. 이 결과를 R1 수정 완료로 보지는 않습니다. 담당 수정 후 위 시나리오와 전체 분석·테스트 결과를 남겨 주세요.

## 5. 완료 기준과 공유할 결과

- 400/422 계산 거절 이후 앱 옷장에 새 결과가 생기지 않습니다.
- 입력·수정 가능 상태를 유지하고 저장 버튼이 다시 동작합니다.
- 저장하지 않았는데 저장 완료 문구·리포트가 나오지 않습니다.
- 정상 계산·직접 입력과 별도 장애 정책에 의도하지 않은 변화가 없습니다.
- 반영 브랜치·정확한 커밋·관련 검사 결과를 공유하고, 통합 시 앱 옷장과 서버 계산 이력 양쪽을 확인합니다.

백엔드의 R1 충족·서버 이력 미저장은 10월 19일 재확인 회신의 보고입니다. 담당자가 후속 변경을 반영했다면 새 커밋을 기준으로 다시 대조하면 됩니다. R4 부위/재촬영 안내나 R5 후보 확인 연결을 기다리지 않고 R1을 진행할 수 있습니다.
