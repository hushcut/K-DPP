# 준원님 전달: 4단계 사용자 확인·부위·재촬영 안내 연동

작성일: 2026-10-14

**지금은 구현을 보류하고 연결 방식만 전달합니다.** 실제 반영 시점은 담당자와 별도로 맞춰 주세요. 이번 문서 작성으로 AI·백엔드·프론트엔드 코드를 변경하지 않았습니다.

## 1. 먼저 연결할 최소 범위: DJ009 간소화안

DJ009처럼 여러 조성 묶음이 있어 자동 선택하지 못한 경우, **검토 후보 1개의 소재·비율을 기존 직접 입력 화면에 미리 채우고 사용자가 확인하거나 수정한 뒤 계산**하는 방식을 제안합니다.

- 사진 분석의 자동 판정은 기존처럼 **HTTP 422·실패**로 유지합니다.
- `detail.materials`는 `{}`로 유지하고, 미리 채울 값만 기존 `detail.partial_materials`로 전달합니다.
- 사용자가 실제 소재명·비율을 보고 확인하기 전에는 계산·저장하지 않습니다.
- 사용자가 바꾼 값이 있으면 그 최종 입력값으로 기존 계산·저장 경로를 사용합니다.
- 새 확인 세션·확인 API·DB 테이블·Vision 재호출은 필요하지 않습니다.
- 이 간소화안은 서버에서 AI 분석을 확인 성공으로 전환하는 방식과 다릅니다. `analyze_ocr_result(..., confirmed_review_id=...)` 재호출은 사용하지 않습니다.

## 2. AI에 이미 준비된 함수

파일: `AI/kdpp_ai_ocr_integrated/apps/service/label_analysis.py`

```python
analyze_ocr_result(ocr_result)
get_ocr_review_options(ocr_result)
```

첫 함수는 자동 성공/실패와 내부 근거를 반환합니다. 두 번째 함수는 **같은 OCR 결과**에서 사람이 검토할 조성 후보 목록을 반환하며, 호출 자체가 소재 확정이나 사용자 확인을 뜻하지 않습니다.

현재 검토 후보는 **0개 또는 1개**입니다. 원본의 첫 조성 묶음이 소재·비율을 온전히 갖췄을 때만 후보를 만듭니다. 앞으로 여러 후보를 지원할 수 있으므로 연결 코드는 **정확히 1개일 때만** 미리 채워 주세요. 0개 또는 여러 개이면 현재의 빈 직접 입력 흐름을 유지합니다.

후보의 `id`, `selection`, `source`, `warnings`, 확인 관련 내부 근거는 간소화안의 앱 응답에 넣을 필요가 없습니다. `materials`만 복사해 사용합니다. 후보 ID는 인증·사용자 소유권 증명 수단도 아닙니다.

## 3. 백엔드 연결 지점

파일: `BACKEND/main.py`

1. 기존 AI import 경로에서 `get_ocr_review_options`를 함께 가져옵니다. AI import 실패 시 기존 오류 처리 정책을 유지합니다.
2. `extract_label_input()`에서 사진 OCR을 수행한 뒤, **이미 받은 `ocr_result`**로 분석과 후보 추출을 수행합니다.
3. 자동 분석이 실패했고 후보가 정확히 1개이면 그 소재·비율만 미리 채울 값으로 보관합니다.
4. `parse_label_materials()`의 기존 422 생성 위치에서 이 값을 `detail.partial_materials`로 전달합니다.
5. `materials`, HTTP 상태, `ai_success`, `parser_error_code`, 기존 경고·관리 지침·미리보기 의미는 유지합니다.

연결 의도를 나타내는 예시이며, 아래 코드는 아직 실제 백엔드에 반영하지 않았습니다.

```python
# 기존 run_ocr(...) 결과를 재사용합니다. 이 단계에서 OCR을 다시 호출하지 않습니다.
parsed = analyze_ocr_result(ocr_result)
prefill_materials = {}

if parsed["status"] == "failed":
    options = get_ocr_review_options(ocr_result)
    if len(options) == 1:
        prefill_materials = dict(options[0]["materials"])

# 이후 기존 422 응답의 detail.partial_materials에만 전달합니다.
# parsed["materials"]에 후보를 넣거나 status를 success로 바꾸지 않습니다.
```

`extract_label_input()`과 실패 응답 생성 위치 사이에 값을 전달하는 방법은 백엔드 구조에 맞춰 정해 주세요. 현재 테스트용 문자열 OCR 또는 `raw_ocr_text` 경로에는 실제 `OcrResult`가 없으므로, 사진 확인 후보를 새로 만들지 않고 기존 처리를 유지합니다.

후보가 다음 값이라면 422의 관련 필드는 아래처럼 전달할 수 있습니다. **소재·비율과 오류 코드는 설명용 예시이며, 실제 값·오류 코드는 해당 분석 결과를 사용합니다.**

```json
{
  "detail": {
    "materials": {},
    "partial_materials": {
      "rayon": 45,
      "nylon": 28,
      "polyester": 22,
      "polyurethane": 5
    },
    "ai_success": false,
    "parser_error_code": "ambiguous_composition"
  }
}
```

위 예시는 기존 오류 응답 전체가 아니라 관련 필드만 발췌한 것입니다. 실제 응답의 message·error_code·warnings·care_instruction·raw_ocr_preview와 최상위 오류 포장은 기존 계약대로 유지합니다.

## 4. 프론트엔드에 이미 있는 흐름

현재 코드에는 아래 연결이 준비돼 있습니다.

| 위치 | 현재 역할 |
|---|---|
| `FRONTEND/lib/services/scan_api_service.dart` | 422의 `partial_materials`를 읽어 `ScanApiException.partialMaterials`에 보관 |
| `FRONTEND/lib/scan/scan_capture_actions.dart` | `_showManualFallback()`에서 부분 소재를 수동 초안으로 전달 |
| `FRONTEND/lib/services/scan_draft_service.dart` | `buildManual()`로 직접 입력 초안을 생성하고 `isManualMaterialMode=true` 설정 |
| `FRONTEND/lib/scan/scan_result_actions.dart` | `_applyScanDraft()`로 편집 폼을 채움 |
| `FRONTEND/lib/scan/scan_save_actions.dart` | 사용자의 최종 편집 소재를 수집해 기존 계산 경로 사용 |

따라서 별도 후보 선택 화면을 먼저 만들기보다 기존 경로를 재사용할 수 있습니다. 다만 **값이 채워져 있다는 이유로 자동 확정·자동 계산하지 않는지**는 앱에서 직접 확인해야 합니다.

권장 안내: “확인이 필요한 후보값입니다. 라벨과 소재·비율을 비교하고, 필요하면 수정한 뒤 확인해 주세요.”

- 잘못된 후보이면 사용자가 전부 수정하거나 지울 수 있어야 합니다.
- 취소·다시 촬영을 선택하면 이전 후보가 다음 사진의 폼에 남지 않아야 합니다.
- 현재 일반 422 안내와 후보값 안내를 어떻게 구분할지는 앱·API 담당자가 함께 정해 주세요. 후보값이 있어도 ‘AI 인식 성공’이라고 표시하지 않습니다.

## 5. 부위 미확정·재촬영 안내는 별도 계약 확인 필요

현재 백엔드는 AI의 `confidence`·`parse_evidence`·`ocr`를 앱 응답에 넣지 않습니다. 아래 내부 근거를 노출하려면 공개할 최소 필드와 화면 문구부터 합의해 주세요. 내부 객체 전체를 그대로 전달하는 방식은 제안하지 않습니다.

| AI 상태·근거 | 의미 | 화면에서 구분할 내용 |
|---|---|---|
| 성공 + `selected_part=generic` + `parse_evidence.part_resolution.status=unidentified` | 소재는 확정됐지만 부위는 모름 | “소재 인식 완료 · 부위 미확인”. 겉감이나 의류 전체 조성으로 단정하지 않음 |
| 성공 + 명시적인 `selected_part` | 해당 부위의 조성을 선택함 | 겉감·안감 등 실제 선택 부위 표시. 안감을 겉감으로 표시하지 않음 |
| 자동 실패 + 검토 후보 1개 | 사람이 조성 선택·확인해야 함 | 위 직접 입력 미리 채우기 |
| 실패 + `parse_evidence.recapture.action=retake_composition_region` | 현재 OCR 근거가 없거나 불완전함 | “소재명·비율·부위가 함께 보이도록 조성 부분을 선명하게 촬영해 주세요.” |
| OCR 서비스 오류·시간 초과 | 사진 품질 문제로 확정할 수 없음 | 현재 오류 종류에 맞는 재시도·직접 입력 안내 |

`recapture.reason`은 `composition_text_missing` 또는 `composition_incomplete`이며, `basis=current_ocr`입니다. **사진이 영구적으로 복구 불가능하다는 뜻은 아닙니다.** 호출 실패·캐시 누락·시간 초과가 있는 분석에는 AI가 이 권고를 붙이지 않습니다. 캐시 누락은 주로 오프라인 QA에서 구분할 상태입니다.

DJ009 최소 연결은 기존 `partial_materials` 계약을 재사용할 수 있습니다. 부위·재촬영의 구조화된 표시는 추가 계약이 필요한 후속 범위로 구분해 주세요.

## 6. 반영 후 완료 확인 항목

- DJ009는 자동 분석 422·`materials={}`를 유지하고 후보만 직접 입력 폼에 표시되는가?
- 후보가 0개이거나 여러 개이면 임의로 첫 항목을 고르지 않는가?
- 사용자가 확인하기 전에는 계산·이력 저장이 발생하지 않는가?
- 확인·수정한 실제 최종 값으로 계산·저장되는가? 잘못된 비율은 기존 입력 검증으로 거절되는가?
- 취소·다시 촬영·다른 사진 입력에서 이전 후보가 사라지는가?
- 정상 성공·후보 없는 실패·인증 만료·서비스 오류·시간 초과의 기존 처리가 유지되는가?
- 후보를 꺼내는 과정에서 Vision 호출·일일 스캔 사용량이 추가되지 않는가?
- 부위 정보가 없는데 겉감으로 표시하거나, 재촬영 권고를 서비스 오류에 붙이지 않는가?
- 사진·OCR 원문·내부 예외·후보 ID 등을 불필요하게 로그나 앱 응답에 노출하지 않는가?

사람이 확인·수정한 결과는 **수동 입력 결과**로 취급하며 자동 OCR 정확도에 합치지 않습니다. 후보를 담아 422를 반환한 로그는 ‘후보 제시’ 기록이고, 사용자가 확인했다는 기록은 아닙니다. 확인율·수정률 추적이 필요하면 별도 계측 범위를 합의합니다.

## 7. 기준 상태와 담당 범위

- 게시 기준: `ai-integration`의 `848a036`. AI 검토 후보·부위 미확정·재촬영 내부 근거는 준비돼 있습니다.
- 현재 로컬에는 별도의 인식 개선 3개 파일이 미커밋 상태입니다. 해당 변경은 DJ023 일본어 회전 복구이며 이번 DJ009 연결 구현과 별개입니다.
- 이 문서는 현재 코드·계약과 앞서 검토한 간소화안을 대조한 **구현 요청서**입니다. 실제 앱·API 연결 완료나 이 제안의 종단 검증 완료를 뜻하지 않습니다.
- AI 담당은 AI 함수와 판정 근거를 지원합니다. 백엔드·프론트엔드의 실제 수정·계약 반영·앱 검증은 각 담당 브랜치에서 진행해 주세요.
- 구현 후 정상 성공·DJ009 확인 필요·DJ015 부위 미확정·DJ014/DJ035 재촬영 필요·서비스 오류를 함께 점검하고 담당 변경을 통합하면 됩니다.
