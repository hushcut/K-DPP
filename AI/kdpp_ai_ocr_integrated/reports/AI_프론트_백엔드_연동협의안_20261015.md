# AI·프론트엔드·백엔드 연동 협의안

작성일: 2026-10-15 (Asia/Seoul)
대상: AI 담당, 프론트엔드·백엔드 담당자
기준: `ai-integration`의 부모 `da62998ef698c5b6599f65070c071185401ade14` 이후 AI·보안 보완

**협의용 초안이며 구현 지시나 합의 완료 문서가 아닙니다.** AI에서 해결할 수 있는 문제는 AI에서 먼저 처리하고, 기존 응답·직접 입력·오류 처리 흐름을 재사용하는 안을 우선 제안합니다. 담당 브랜치의 후속 변경이 있으면 실제 최신 코드와 대조해 주세요.

AI의 A1 재촬영 분류와 A2 좌표 경계 보완, 최종 저장 평가·노션 원고와 공통 자동 보안 구성을 함께 정리했습니다. AI·QA 회귀 4,581건·격리 DB 연동 14건·보안 검사 22개를 통과했고, 로컬 커밋/푸시 전 훅을 설치했습니다. 게시 커밋의 원격 CI는 GitHub에서 별도 확인합니다. 실제 노션에는 아직 반영하지 않았습니다. 아래에서 ‘현재’는 확인한 코드 상태, ‘제안’은 아직 구현하지 않은 내용입니다. A1·A2 완료 범위는 3절, 최신 수치의 근거는 [AI 최종 평가](AI_최종평가_20261015.md)에 기록합니다. FRONTEND/BACKEND 수정·새 Vision 호출·외부 메시지 전송은 하지 않았습니다.

## 1. 먼저 함께 결정하고 싶은 내용

AI가 잘못 읽은 결과를 고치는 일과, 올바르게 읽은 소재에 계산 기준이 없는 일은 구분해야 합니다. 다른 파트의 작업을 줄이기 위해 소재를 바꾸거나 임의 계수를 넣는 방식은 제안하지 않습니다.

## 2. 확인한 현재 AI 상태

- 대표 조성은 겉감·겉감2를 우선합니다. 관측된 우선 겉감이 불완전하면 완성된 안감·배색으로 대신 성공하지 않습니다.
- 예: `겉감 면 95% / 안감 면 100%`는 `incomplete_part_composition` 실패이며 최상위 `materials`, `parts`는 비어 있습니다. 확인된 보조 부위는 내부 근거에만 보존합니다.
- 겉감이 확정되면 안감 오류로 정상 겉감 결과를 버리지 않습니다. 겉감 근거가 없는 입력은 다른 부위를 평가할 수 있습니다. OCR에 겉감 표기가 없다고 실제 겉감이 없다고 단정하지 않습니다.
- `selected_part=generic`인 성공은 소재 조성은 확정됐지만 부위를 모르는 상태입니다. 겉감이나 의류 전체 조성으로 자동 표시하면 안 됩니다.
- AI의 `high/medium/low`는 검증된 정답 확률이 아닙니다. 사용자 확인 후보와 재촬영 근거도 자동 성공을 뜻하지 않습니다.
- 최신 수정본의 AI·QA 전체 회귀 4,581건·격리 DB 연동 14건·보안 검사 22개가 통과했습니다. 좌표/재촬영 관련 816개는 전체 회귀에 포함됩니다. 부모 `da62998`의 [AI 검사](https://github.com/hushcut/K-DPP/actions/runs/38528889218)와 [전체 CI](https://github.com/hushcut/K-DPP/actions/runs/38528889530)는 과거 성공 기록이며, 새 게시 커밋의 원격 결과는 별도 확인합니다.
- 저장 OCR 평가에서 같은 실사진 50장의 두 기록은 각각 평가 대상 48장 중 소재 44장·소재와 정답 대표 부위 43장이 일치했습니다. 성공 44건 중 **32건은 `generic`**, 정답지의 겉감 항목에서는 **11/14**가 소재·겉감 일치입니다. 부위 미확정의 표시와 계산 기준을 먼저 결정해야 합니다.
- 원본 10개 계열의 변형 200건은 소재·부위 185건이 일치하며 실패 15건이 남습니다. `generic` 정답과의 일치를 명시적인 겉감 확인으로 세지 않습니다. 새로운 의류의 실시간 Vision 정확도나 앱 종단 성능은 아닙니다.

## 3. AI에서 먼저 처리할 항목

### A1. 새 겉감 실패의 재촬영 분류

게시 기준 `da62998`의 `_with_recapture_guidance()`는 `composition_not_found`만 대상으로 해, 정상 완료된 OCR에서 겉감 불완전으로 실패한 경우 재촬영 근거가 빠졌습니다.

**10/15 AI 구현·로컬 검증 완료:** AI 내부에서 `incomplete_part_composition`을 대상에 포함했습니다. 모든 OCR 시도가 정상 완료된 불완전 조성에만 재촬영 근거를 추가하며, 같은 오류 코드 안의 서로 다른 조성 충돌은 별도로 제외합니다. 서비스 오류·시간 초과·캐시 누락·사용자 검토 후보가 있는 경우도 제외합니다.

최상위 실패·빈 소재 결과는 유지합니다. 문구 개선을 이유로 성공으로 바꾸거나 다른 부위를 계산용 조성으로 넣지 않습니다. 기존 앱의 일반 422 직접 입력 흐름은 계속 사용할 수 있습니다.

[재촬영 검사](../tests/test_recapture_guidance.py)에 21개 사례를 추가해, 수정 전 6개 사례에서 안내 누락을 재현했습니다. 수정 후 관련 9개 파일의 262개 검사가 통과했습니다. 저장 평가 응답 300건의 진단 재분류에서도 기존 결과는 유지됐습니다. OCR 파이프라인 전체 재실행이나 새 Vision 정확도 측정은 아니며, 기존 전체 4,531개 회귀를 이번 수정 후 재실행한 것으로 표현하지 않습니다. 이 구현은 내부 근거 추가까지이며 앱 표시용 새 경고 코드는 여전히 협의 전 제안입니다.

### A2. 인식 개선과 회귀 검증

- 같은 사진·부위·행의 근거를 확인하는 일반화 가능한 보정만 추가합니다. 사진 번호별 조건·오독의 무분별한 별칭 등록·누락 비율 추정은 사용하지 않습니다.
- 겉감 확정/미확정, 다른 부위만 존재, 부위 미확정, 여러 조성, 미등록 소재, 서비스 오류를 함께 검사합니다.
- 소재 일치·부위 일치·오답 성공·안전한 거절·실제 RPC 수·처리시간을 분리합니다. 새 정책에 따른 DJ045의 안감 대체 거절을 단순한 성능 퇴행으로만 해석하지 않습니다.
- 19일 전 전면 리팩터링이나 세탁기호 모델 도입은 우선 범위에 넣지 않습니다. 단일 세탁기호 분류 실험을 전체 라벨의 제품 기능으로 설명하지 않습니다.

**10/15 AI 적용·로컬 검증 완료:** 엄격한 기울기 판정에서 구역이 없을 때만 두 변의 경계에 최대 1픽셀을 반영했습니다. 기존 구역·모호함·글자·숫자·좌표는 보존했습니다. DJ038 일본어 회전 복구로 저장 변형 자료는 184→185/200, 실사진 결과는 유지됐습니다. 신규 29개 포함 관련 816개 검사를 통과했으며 [원인 분석](남은_인식실패_공통원인_20261015.md)과 [최종 평가](AI_최종평가_20261015.md)에 남은 근거와 부위 미확정을 기록했습니다. 앱 전달용 새 코드나 필드를 합의 없이 추가하지 않았습니다.

## 4. 인식 지원과 계산 지원: AI를 억지로 축소하지 않는 안

현재 AI 소재 사전은 26종, 서버 시드의 계산 소재는 22종입니다. `acetate`, `alpaca`, `hemp`, `triacetate`는 AI에서 100% 조성으로 성공할 수 있으나 현재 서버 시드의 표준명·별칭에는 없습니다. 배포 DB가 다른 경우에는 실제 `/materials`와 맞춰 확인해야 합니다.

서버는 이미 `material_details[].is_supported`를 제공하고, 프론트의 `ScanMaterialDetail`에도 `isSupported` 필드가 있습니다. 탄소 계산 오류의 `unknown_materials`와 400/422 → `CarbonApiErrorType.badRequest` 분류도 있습니다.

**최소 제안:**

1. AI는 인식한 실제 소재명을 유지합니다. 미지원 소재를 면/폴리에스터 등으로 바꾸거나 나머지 비율을 채우지 않습니다.
2. 프론트는 이미 받은 지원 여부로 “소재는 인식했지만 계산 기준이 없습니다”를 표시하고 수정 가능한 기존 폼을 유지합니다. 편집 후 값에는 서버 카탈로그 확인 또는 기존 계산 API 검증을 다시 적용합니다.
3. 미지원 소재처럼 서버가 요청을 명시적으로 거절한 경우는 로컬 기본계수로 계산·저장하지 않는 안을 제안합니다. 모든 소재가 지원돼도 합계·기타 입력 검증은 계속 필요합니다.
4. 네트워크·일시 장애 때 임시 추정을 허용할지는 별도 정책으로 결정합니다. 허용한다면 서버 확정값과 구분하고, 입력 오류에까지 같은 대체 저장 정책을 적용하지 않습니다.
5. 새 소재의 계수 추가는 검토된 출처와 적용 범위가 확보된 뒤 서버 담당이 관리합니다. AI 안에 서버의 22종 목록을 복제하면 목록이 바뀔 때 또 어긋나므로 우선 권장하지 않습니다.

**프론트 최소 변경 지점:** 현재 `_submitClothes()`는 인증 오류 외의 `CarbonApiException`에서도 로컬 저장을 계속합니다. 명시적인 입력 거절 분기와 “임시 추정값으로 저장했어요” 안내를 함께 검토해 주세요. 문구만 바꾸거나 저장 분기만 바꾸면 서로 다른 사실을 안내하게 됩니다. 백엔드는 기존 지원 여부·거절 응답을 유지하면서 현재 카탈로그와 맞는지 확인하면 됩니다.

소재만 별도로 저장하고 탄소량을 ‘미산정’으로 두는 방식은 장기 대안입니다. 기존 저장 모델을 바꿀 수 있으므로 이번 최소안의 필수 조건으로 삼지 않습니다.

## 5. 부위·재촬영 안내: 기존 전달 경로를 활용하는 안

현재 백엔드는 AI의 `warnings`를 앱에 전달하지만, 앱은 이를 표시하지 않습니다. `selected_part`, `parse_evidence` 등 내부 정보도 앱의 스캔 모델로 연결되지 않습니다. 오류 화면은 주로 HTTP 상태에 따른 고정 문구를 사용하므로 **AI의 `message`만 바꿔서는 세부 안내가 화면에 나타나지 않습니다.**

| 대안 | 변경 범위 | 판단 |
| --- | --- | --- |
| 기존 `warnings` 활용 | AI가 합의한 공개 코드 추가, 프론트가 알려진 코드만 해석. 백엔드는 기존 전달을 유지하고 검사 | 19일 전 최소안으로 우선 검토. 별도 API·DB·새 화면 없이 기존 안내 영역을 활용할 수 있음 |
| 명시적인 공개 부위/안내 필드 | AI가 최소 공개 필드 정리, 백엔드 응답과 프론트 모델·화면 연결 | 의미와 자료형이 명확한 장기안. 실제 호출 지점의 변경량과 일정 확인 후 선택 |

최소안에서 사용할 수 있는 **미구현 코드 예시**는 `composition_part:outer`, `composition_part:lining`, `composition_part:unidentified`, `composition_action:retake_composition_region`입니다. 이 이름과 전체 부위 목록은 합의 후 확정합니다. 소재 불완전·서비스 오류·검토 필요 상태를 모두 같은 경고로 표현하지 않습니다.

- 선택된 부위는 AI가 정합니다. 프론트·백엔드가 경고의 유무만으로 부위를 추측하거나 별도 우선순위를 구현하지 않습니다.
- 프론트는 알려진 코드만 사용자 문구로 바꾸고 알 수 없는 내부 경고를 그대로 노출하지 않습니다. 성공·422 양쪽에서 필요한 코드가 유지되는지 확인합니다.
- 새 코드를 이해하지 못하는 기존 앱이 기본 성공/실패 처리를 유지하도록 합니다. 다만 해당 앱이 부위 표시까지 지원한 것으로 보지는 않습니다.
- 보조 부위의 `confirmed_parts`·원문·좌표·호출 기록·내부 검토 ID 전체를 공개할 필요는 없습니다.
- 실제 부위를 다음 화면까지 보존해야 한다면 프론트의 초안 전달은 필요합니다. 기존 `warnings`로 화면 표시를 줄여 연결해도 저장 이력에 부위가 보존되는 것은 아닙니다. 이력 보존은 별도 범위로 합의합니다.

**추천:** AI의 분류·코드 생성을 먼저 준비하고 공개 코드 목록을 합의한 뒤, 프론트가 기존 안내 영역에 연결하는 최소안을 우선 검토합니다. 백엔드의 추가 가공이 불필요하면 새 응답 변환 로직은 만들지 않습니다. 팀이 경고를 정보 전달 수단으로 쓰지 않기로 결정하면 명시적 필드안을 선택합니다.

## 6. DJ009 확인 후보: 기존 보류를 유지한 협의 항목

이 항목은 기존 요청에 따라 구현 보류 상태입니다. 이번 협의안 작성이 보류 해제나 앱 연결 완료를 뜻하지 않습니다.

연결하기로 결정한다면 [기존 전달 문서](준원_4단계_사용자확인_연동요청_20261014.md)의 직접 입력 폼 재사용안을 검토합니다. 해당 문서 7절의 `848a036`·미커밋 3개 파일 설명은 작성 당시 기록이며, 이 협의안의 부모 기준은 `da62998`, 이후 보완 내용은 2·3·7절을 따릅니다.

- AI는 `get_ocr_review_options()`의 후보 적격성·출처·검사를 담당합니다. 확인 후보는 자동 성공이나 겉감 확정이 아닙니다.
- 백엔드는 이미 받은 동일 `OcrResult`를 재사용해 후보가 정확히 1개일 때만 `detail.partial_materials`에 복사하는 연결을 검토합니다. 새 Vision 호출·확인 세션·DB 테이블은 최소안에 필요하지 않습니다.
- 자동 판정은 422·실패와 `materials={}`를 유지합니다. 겉감 미확정 실패의 보조 부위 정보를 임의로 후보값에 채우지 않습니다.
- 프론트의 기존 직접 입력 폼을 사용하고, 사람이 실제 값을 확인·수정하기 전에는 계산·저장하지 않습니다. 취소·재촬영·다른 사진에서 후보가 남지 않아야 합니다.
- 수동 확인한 결과를 자동 OCR 성공률에 합치지 않습니다. 후보를 반환한 것과 사용자가 확인한 것도 구분합니다.

일정상 연결하지 않으면 현재 빈 직접 입력 흐름을 유지하고 노션에 ‘AI 후보 함수 준비·제품 연결 미완료’로 기록합니다.

## 7. 탄소 근거·운영·보안의 담당 경계

**탄소 근거:** 현재 서버 계수는 개발용 추정값이며 승인된 출처 확인이 남아 있습니다. 프론트·서버의 계수 숫자 동기화는 현재 코드에서 이미 맞춰져 있으므로 같은 수정을 반복할 필요는 없습니다. 주요 소재의 출처·단위·적용 범위를 먼저 확정하고, 기존 `calculation_scope`, `calculation_basis`, `calculation_source`, `calculation_note`를 재사용할 수 있는지 검토합니다.

겉감 조성과 의류 전체 추정 무게를 사용하는 계산은 부위별 실제 무게를 합산한 의류 전체 LCA가 아닙니다. ‘대표 조성에 기반한 소재 생산 단계 추정’이라는 가정을 설명하고 세탁·사용·폐기 배출이나 검증된 수명 예측까지 구현한 것처럼 표시하지 않습니다. AI가 임의로 계수를 정해 출처 문제를 대신 해결하지 않습니다.

**운영:** AI는 후보별 결과·시간·실제 RPC 수·재시도 수를 내부 메타데이터로 제공할 수 있습니다. OCR 후보 개수와 실제 호출 수는 같지 않을 수 있습니다. 운영 로그에 필요한 항목만 백엔드가 선택하고, 앱에 전체 메타데이터를 노출할 필요는 없습니다. 실제 비용·지연은 운영 조건에서 별도 측정하며 새 유료 호출은 승인된 범위에서만 합니다. 독립 AI HTTP 서비스는 기본 로컬 주소로 실행되며, 별도 인증/한도 없이 공개하는 배포안은 이번 최소안에 포함하지 않습니다.

**보안:** AI 파일 제외 경로 193개·기존 추적 AI 172개를 검사했고, 공통 Gitleaks 검사기와 커밋/푸시 전 훅을 현재 폴더에 설치했습니다. 가짜 키 차단·정상 커밋/푸시 허용·중간 커밋/메시지 검사를 포함한 22개 검사가 통과했습니다. 두 브랜치의 로컬 이력도 검사했으며 OCR 이미지 해시 오탐만 정확한 객체·규칙·줄로 예외 처리했습니다. 보안 CI 구성은 함께 관리하고 게시 커밋의 GitHub 실행 결과를 확인합니다. `kyh/ai` 코드 반영·새 PC 훅 설치·관리자 푸시 보호/필수 검사 설정은 남아 있습니다. 설치 명령과 범위는 루트 `GIT_SECURITY.md` 8절을 따릅니다. 키·서비스 계정·실제 환경 파일·DB·OCR 전체 원문·실사진·로컬 산출물을 공유 문서/노션/CI artifact에 넣지 않습니다.

## 8. 함께 확인할 최소 시나리오

아래는 **완료를 판단할 검사 기준**이며, 이 협의안으로 앱 실기기 검사가 끝난 것은 아닙니다. AI 단위 검사는 AI 담당이, API·앱 검사는 해당 담당자가 수행합니다.

| 입력·상황 | AI/서버 기준 | 앱에서 확인할 동작 |
| --- | --- | --- |
| 겉감 면 100%, 안감 폴리에스터 100% | 대표 조성은 겉감 면 100% | 겉감 기준임을 알리고 해당 소재로 계산 |
| 겉감 면 95%+미확실, 안감 면 100% | 자동 실패, 계산용 소재 비움 | 안감으로 자동 대체하지 않고 재촬영/직접 확인 안내 |
| 겉감 근거 없이 명시적인 안감 조성만 확인 | 실제 선택 부위는 안감 | 겉감으로 표시하지 않음. 다른 부위를 사용한다는 근거 표시 |
| 부위 표기 없는 완전한 조성 | `generic`, 부위 미확정 | 겉감/의류 전체 조성으로 단정하지 않고 안내 |
| 아세테이트 등 계산 미지원 소재 | 소재 인식 결과와 계산 지원 여부 분리 | 임의 다른 소재/계수로 확정 저장하지 않고 수정 안내 |
| 계산 API의 400/422 입력 거절 | 기존 오류 범주·미지원 목록 활용 | 검증 오류를 네트워크 장애와 같은 저장 분기로 처리하지 않음 |
| 확인 후보 1개/0개, 취소·다른 사진 | 연결을 선택한 경우에만 후보 전달 | 명시 확인 전 계산하지 않음. 후보가 없거나 취소되면 잔류값 없음 |
| 인증 만료·네트워크 장애·OCR 시간 초과 | 기존 API 계약과 원인 구분 유지 | 재로그인/재시도/직접 입력 안내가 섞이지 않음 |

계산 오류를 막는 과정에서 수정 가능한 입력까지 사라지지 않게 하고, 정상 지원 소재·기존 수동 입력·취소·재촬영도 함께 검사합니다. 기존 사진을 복구하더라도 원본 근거와 충돌하는 성공을 늘리지 않습니다.

이 표는 목표 일정이며 담당자의 작업 약속이 아닙니다. 17일까지 연결이 어렵다면 AI 검증과 기존 직접 입력 흐름을 완료 범위로 분리하고, 제품 미연동 항목을 명확히 남깁니다.

노션에는 심사 기준에 맞춰 다음 근거를 연결합니다.

- 문제 정의: 어떤 사용자가 소재·부위 입력에서 어려움을 겪고 계산값이 어떻게 왜곡되는가.
- 혁신·창의성: 외부 Vision과 직접 구현한 다국어/좌표/겉감 우선/거절 규칙의 역할, 동일 조건 비교와 비용 근거.
- 가능성·완성도: 위 일정·실제 달성 범위·사용자 실패 처리, 운영비/수익 모델에 필요한 팀 결정. 수익 모델은 AI 구현 성과로 대신 쓰지 않음.
- 소통·전달력: 각 항목을 ‘요청 전달 / 검토 / 합의 / 담당 반영 / 통합 검증’으로 나눠 담당·날짜·커밋·검사 결과를 기록. 문서 전달을 앱 구현 완료로 세지 않음.

1학기 실험 기록은 당시 기준으로 보존하고, 현재 프로젝트 현황과 2학기 개선 기록을 최신 코드/검증으로 갱신합니다. 사진별 개발 자료·변형 이미지·사용자 확인 결과를 독립 실사진 자동 정확도로 합산하지 않습니다.
