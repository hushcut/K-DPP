# 팀원 전달용: AI 연동 현황과 프론트·백엔드 협의 요청

작성일: 2026-10-15 (Asia/Seoul)
대상: 프론트엔드·백엔드 담당자, AI 담당
확인 기준: `ai-integration`의 `acdaa61c5d5c25002bed1ef5e4d56153f863d3c7` (`acdaa61`)
문서 상태: 팀 검토 요청. 아래 요청·제안은 담당자의 합의나 구현 완료를 뜻하지 않습니다.

## 1. 전달 메시지

AI 쪽 겉감 우선 판정, 불완전 조성 거절, 재촬영 근거와 좌표 보정은 수정·검증 후 게시했습니다. 현재 제품 연결에서 가장 먼저 맞춰야 할 것은 **계산 입력을 거절당한 결과를 임시 탄소값으로 저장하지 않는 것**입니다.

AI가 인식한 소재를 바꾸거나 임의 계수를 추가하는 방식으로 이 문제를 해결할 수는 없습니다. 프론트에서는 기존 오류 분기·직접 입력 폼·소재 지원 여부를 재사용하고, 백엔드에서는 기존 거절 응답과 실제 소재 카탈로그가 일치하는지 확인하는 최소 변경을 요청드립니다.

추가로 겉감·안감·부위 미확정과 재촬영 안내를 화면에 연결할 방법, 탄소계수 출처를 함께 결정하고 싶습니다. **AI가 완료한 항목은 다시 구현할 필요가 없고**, 아래 담당별 요청과 회신표를 기준으로 가능한 범위·예정일을 알려주시면 됩니다. 각 담당 브랜치에 이미 반영한 변경이 있다면 해당 커밋으로 대조하겠습니다.

- 새 실사진 일반화·최신 Vision 정확도·앱 실기기 통합 완료를 입증한 결과는 아닙니다. 상세 기준은 [AI 최종 평가](AI_최종평가_20261015.md)에 있습니다.

이번 문서 정리에서는 코드를 읽어 현황을 대조했습니다. 프론트·백엔드 수정, 새 Vision 호출, DB·기존 캐시 갱신, 새 통합 검사는 하지 않았습니다.

## 3. 공통으로 유지해야 할 판정 기준

| 입력·상태 | 유지할 결과 |
| --- | --- |
| 겉감 면 100%, 안감 폴리에스터 100% | 대표 조성은 겉감 면 100% |
| 겉감 면 95%+나머지 미확실, 안감 면 100% | 자동 실패. 안감으로 대체하지 않고 재촬영·직접 확인으로 연결 |
| 겉감 근거 없이 안감 등 다른 부위만 확인 | 다른 부위를 평가할 수 있지만 실제 선택 부위를 표시 |
| 완전한 조성이나 부위 표기가 없음 | `generic`: 부위 미확정. 겉감·의류 전체 조성으로 단정하지 않음 |
| 소재는 인식됐으나 계산 기준이 없음 | 인식 성공과 계산 불가를 구분. 소재명 변경·임의 계수 확정 금지 |
| OCR 서비스 오류·시간 초과 | 소재 인식 실패·입력 검증 오류와 구분해 재시도 또는 직접 입력 안내 |

**OCR에 겉감 표기가 없다는 사실은 실제 라벨에 겉감이 없다는 증거가 아닙니다.** 부위 미확정의 화면 표시와 계산 진행 조건을 함께 합의해야 합니다. AI의 `high/medium/low`도 검증된 정답 확률로 표시하지 않습니다.

R1·R2는 새로운 AI 기능이나 부위 API를 기다리지 않고 진행할 수 있습니다. R3의 근거 확인도 병행합니다. R4는 공개 정보의 이름·의미를 먼저 합의한 뒤 연결합니다.

### R1·R2. 미지원 소재와 계산 오류 처리

**현재 코드에서 확인한 흐름**

- AI 소재 사전은 26종, 서버 `MATERIAL_SEEDS`는 22종입니다. `acetate`·`alpaca`·`hemp`·`triacetate`는 AI에서 인식할 수 있지만 현재 시드의 표준명에 없습니다. 운영 DB의 실제 지원 여부는 담당자가 `/materials`와 대조해야 합니다.
- `POST /api/scan`은 `material_details[].is_supported`를 제공합니다. 프론트 `ScanMaterialDetail.isSupported`도 이미 있습니다.
- `POST /api/carbon/calculate`는 미지원 소재를 `400 / MATERIAL_NOT_FOUND`와 `unknown_materials`로 거절합니다. 비율 등 입력 오류도 기존 검증으로 거절합니다.
- 프론트는 계산 API의 400/422를 `CarbonApiErrorType.badRequest`로 분류합니다. 하지만 `_submitClothes()`는 인증 오류 외의 `CarbonApiException`을 잡은 뒤에도 `provider.addClothes()`로 진행합니다.
- 미지원 소재의 로컬 배출계수 기본값은 `10.0`입니다. 오류 문구에도 “기준이 없어 임시 추정값으로 저장했어요”가 있어 저장 분기와 문구를 함께 바꿔야 합니다.

**프론트 요청**

1. 계산 API의 명시적인 400/422 입력 거절은 저장으로 진행하지 않고 현재 폼에서 수정·재촬영할 수 있게 해 주세요. 저장 버튼의 로딩 상태도 해제해야 합니다.
2. `isSupported=false`인 소재는 인식 결과에 남기고 “소재는 인식했지만 탄소 계산 기준이 없습니다”로 안내해 주세요. 미지원이라는 이유로 다른 소재를 고르게 하거나 조성을 임의 변경하지 않습니다.
3. 사용자가 실제 라벨을 보고 소재·비율을 수정한 경우에는 수정한 값으로 서버 카탈로그 확인 또는 기존 계산 API 검증을 다시 적용해 주세요. 최초 스캔의 지원 여부만 재사용하면 안 됩니다.
4. 저장을 중단한 경우에는 “저장했어요” 문구나 저장 완료 화면이 나오지 않게 해 주세요. 정상 지원 소재와 기존 직접 입력의 계산·저장 흐름은 함께 검사합니다.

**백엔드 요청**

1. 실제 카탈로그와 `is_supported`·`unknown_materials`의 일치를 확인해 주세요. 미지원 소재·잘못된 비율 거절 시 서버 이력에도 저장되지 않아야 합니다.
2. 기존 API와 오류 범주를 재사용하면 됩니다. 새 소재 추가는 승인된 탄소계수 근거가 확보된 경우에만 진행하고, 시드 목록만 고쳐 기존 DB까지 변경된 것으로 처리하지 않습니다.
3. 소재 표 변경이 필요하면 현재 프로젝트의 마이그레이션·계약 검사 절차를 담당 브랜치에서 적용해 주세요.

**별도 정책 결정:** 네트워크 장애·서버 장애·인증 만료의 로컬 저장 정책은 입력 거절과 구분해 합의합니다. R1 수정 때문에 모든 오류의 기존 동작을 한 번에 바꾸지는 않습니다. 소재만 저장하고 탄소량을 ‘미산정’으로 두는 대안은 저장 모델 영향이 있어 이번 최소안과 별도로 검토합니다.

### R3. 탄소계수 근거와 설명

현재 서버 소재계수는 코드에 **개발용 추정값**으로 명시돼 있습니다. 다음을 팀에서 확정해 주세요.

- 각 계수의 출처, 단위 `kg CO2eq/kg textile`, 소재·공정·지역 등 적용 범위, 승인 담당자와 날짜
- 겉감 등 대표 조성과 의류 추정 무게를 사용한다는 가정 및 결과의 한계
- 앱·노션에서 같은 범위로 설명할 문구

기존 응답의 `calculation_scope`, `calculation_basis`, `calculation_source`, `calculation_note`를 우선 활용합니다. 코드에 설명 필드가 있다는 사실과 출처 검증 완료는 구분합니다.

현재 계산을 겉감·안감의 실제 무게를 각각 측정한 의류 전체 LCA로 설명하면 안 됩니다. 세탁·사용·폐기 단계 배출이나 검증된 의류 수명 예측이 포함된 결과로 표시하지 않습니다. AI에서 임의 계수를 정해 근거 문제를 대신 해결하지 않습니다.

### R4. 부위·재촬영 안내 연결

**현재 상태:** 백엔드는 성공 응답과 422의 `detail.warnings`에 AI 경고를 전달합니다. 프론트의 스캔 결과 모델에는 부위·경고 연결이 없고, 오류 안내는 주로 HTTP 상태별 문구를 사용합니다. AI의 내부 `selected_part`·`parse_evidence.recapture`를 준비하거나 `message`만 바꾸는 것으로는 화면 연결이 끝나지 않습니다.

**기한 내 우선 제안:** 기존 `warnings: string[]`에 합의된 공개 코드를 넣어 기존 안내 영역에서 표시합니다. 새 API·DB 없이 가능한지 담당자가 확인해 주세요. 팀이 명시적 부위/안내 필드를 선호하면 그 안으로 확정하되 응답·앱 모델 변경 범위를 함께 정합니다.

아래는 **합의 전·미구현 예시**입니다. 현재 응답에 이미 들어오는 코드로 사용하지 않습니다.

| 제안 코드 예시 | 의미·출력 조건 |
| --- | --- |
| `composition_part:outer` | AI가 성공 결과의 겉감을 선택한 경우 |
| `composition_part:lining` | AI가 성공 결과의 안감을 선택한 경우 |
| `composition_part:unidentified` | 성공했으나 `generic`으로 부위를 확정하지 못한 경우 |
| `composition_action:retake_composition_region` | AI가 재촬영 근거를 확인한 실패에만 사용 |

전체 부위 목록·이름·실패 시 출력 조건은 합의 후 AI가 정리합니다. 실패에 보존된 안감 근거를 성공 부위 코드로 내보내지 않고, 서비스 오류·모호한 복수 조성을 일괄 재촬영으로 바꾸지 않습니다.

| 담당 | 합의 후 작업 |
| --- | --- |
| AI | 공개 코드/필드 생성과 검사. 현재 성공·실패 판정 및 소재 결과 유지 |
| 백엔드 | 성공·422에서 합의 정보를 보존하는지 검사. 기존 전달로 충분하면 추가 변환 불필요 |
| 프론트 | 성공 모델과 오류 모델 양쪽에서 해석·표시. 알려진 코드만 문구로 바꾸고 내부 경고를 그대로 노출하지 않음 |

`generic`의 계산 진행 조건도 함께 회신해 주세요. **추천은 ‘부위 미확정 표시 → 기존 폼에서 사용할 소재·비율을 사람이 확인 → 계산’**입니다. 재촬영까지 계산을 보류하는 안도 선택할 수 있습니다. 아직 확정된 제품 정책이나 구현은 아닙니다. 이 확인은 아래 DJ009의 복수 조성 후보 연결과 별개입니다.

선택한 부위를 저장 이력까지 유지할지는 별도 범위입니다. 화면에서 `warnings`를 표시했다고 이력에도 부위가 저장된 것으로 기록하지 않습니다. 전체 원문·좌표·호출 기록·내부 검토 ID를 앱에 전달할 필요는 없습니다.

### R5. DJ009 확인 후보

**구현 보류를 유지합니다.** 재개하기로 합의한 경우에만 [기존 사용자 확인 연결안](준원_4단계_사용자확인_연동요청_20261014.md)을 적용 범위에 맞춰 갱신합니다.

최소안은 이미 받은 동일 OCR에서 적격 후보가 정확히 1개일 때 기존 `detail.partial_materials`와 직접 입력 폼을 재사용하는 것입니다. AI 후보 함수가 준비됐다는 사실을 앱 연결 완료로 세지 않습니다. 사람이 소재·비율을 확인하기 전에는 계산하지 않으며, 자동 실패·빈 최상위 소재는 유지합니다. 재촬영·취소·다른 사진에서 이전 후보가 남지 않아야 합니다. 새 Vision 호출·후보 전용 DB는 이 최소안에 필수적이지 않습니다.

## 6. 통합 완료를 판단할 검사표

아래는 **앞으로 수행할 검사 기준**입니다. 현재 앱 실기기 통과 기록이 아닙니다. 먼저 저장 OCR·모의 응답과 임시 테스트 DB로 검사하고, 실제 앱 확인 결과를 별도로 남깁니다. 새 유료 OCR 호출은 대상·한도를 정한 뒤에만 수행합니다.

| 번호 | 시나리오 | 기대 결과 |
| --- | --- | --- |
| T1 | 겉감 면 100% + 안감 폴리에스터 100% | 겉감 면으로 정상 계산·저장. 안감으로 변경되지 않음 |
| T2 | 겉감 면 95%+미확실 + 안감 면 100% | 422·계산용 소재 비움. 계산·저장하지 않고 확인/재촬영 |
| T3 | 겉감 근거 없이 안감 조성만 확인 | 선택 부위를 안감으로 표시. 겉감 확인 완료로 표시하지 않음 |
| T4 | `generic` 성공 | 부위 미확정 표시 및 합의한 사용자 확인/계산 보류 정책 적용 |
| T5 | 아세테이트 등 계산 미지원 소재 | 소재 인식 결과 유지, 계산 불가 안내. 임의 기본계수 저장 없음 |
| T6 | 계산 API 400/422, 비율 오류·편집 후 미지원 값 | 로컬 옷장·서버 이력에 새 결과 없음. 입력 유지·저장 버튼 복구 |
| T7 | 정상 지원 소재·기존 직접 입력 | 수정 후에도 기존 정상 계산·저장 성공 |
| T8 | 스캔 서비스 오류·시간 초과, 계산 네트워크/인증 오류 | 원인별 안내·합의한 정책 유지. 입력 거절과 혼동하지 않음 |
| T9 | 알려진/새로운 경고 코드, 성공·422 응답 | 알려진 코드 표시·미지원 코드 안전 처리. 원시 내부 정보 노출 없음 |
| T10 | DJ009 후보 1개/0개·취소·다른 사진 | 재개한 경우에만 수행. 명시 확인 전 계산 없음, 이전 후보 잔류 없음 |

검사 기록에는 **담당 브랜치·정확한 커밋·기기/환경·입력 종류·예상/실제 결과·통과 여부**를 적습니다. 실제 사진 호출, 저장 OCR 재생, API 모의 응답, 앱 실기기를 구분합니다. 담당 코드의 기본 검사와 통합 시나리오 검사를 모두 수행한 뒤 완료로 표시합니다.

## 7. 팀 공통 보안 안내

설치 방법은 [저장소 README](../../../README.md#개발-전-필수-보안-설정)에 게시했습니다. 공통 보안 파일이 반영된 최신 코드를 받은 뒤, 커밋·푸시하는 각 팀원이 새 clone·새 PC마다 저장소 루트에서 Python 3.11 이상으로 한 번 실행합니다.

```sh
python scripts/security/setup.py
```

- `ai-integration`의 보안 구성 게시·CI 성공과 다른 브랜치/PC 적용 완료는 구분합니다. `kyh/ai` 반영은 남아 있습니다. 담당 브랜치에도 공통 보안 구성을 정상 통합 절차로 반영한 뒤 설치합니다.
- 설치된 훅은 이후 같은 작업 폴더의 새 세션에도 적용됩니다. 공통 보안 구성이 없는 브랜치에서는 커밋·푸시가 차단될 수 있습니다. 기존 훅 충돌 시 우회하지 않고 확인합니다.
- 로컬 훅은 게시 전 검사, GitHub CI는 게시 후 검사입니다. 관리자 푸시 보호·필수 검사 설정은 별도 확인 항목입니다.
- 공유 문서·노션·CI 산출물에 실제 키·서비스 계정·환경 파일·DB·실사진·OCR 전체 원문을 넣지 않습니다. 상세 범위는 [GIT_SECURITY.md](../../../GIT_SECURITY.md)를 따릅니다.
