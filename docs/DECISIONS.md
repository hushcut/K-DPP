# 결정 기록

프로젝트 레벨 결정 기록이다. Codex와 Claude가 함께 쓴다.

## D-01 부위 조성이 확인되지 않으면 하위 부위로 대체하지 않는다

- 날짜: 2026-09-18
- 상태: 적용됨 (`AI/kdpp_ai_ocr_integrated/apps/text/parse_label.py`)

라벨이 겉감 같은 상위 부위를 명시했는데 그 부위의 혼용률이 확정되지 않으면,
안감처럼 우연히 합이 맞은 다른 부위 값을 최상위 `materials`로 올리지 않고
`incomplete_part_composition`으로 실패를 반환한다.

이유: 안감 소재로 탄소배출량을 계산해 저장하는 조용한 오답이 실패보다 위험하다.
백엔드는 이미 `materials`가 비면 422를 반환하므로 백엔드 변경이 필요 없다.

## D-02 소재 사전이 해석하지 못한 섬유형 토큰이 있으면 그 부위를 확정하지 않는다

- 날짜: 2026-09-18
- 상태: 적용됨 (`apps/text/material_extraction.py`의 `unresolved_material_tokens`)

미등록 토큰이 소재 자리를 차지하면 그 비율이 옆 소재로 재배정되므로,
아래 세 경우에 한해 해당 부위를 확정하지 않는다.

1. CJK 섬유 접미(`纶` `纤维` `丝` 등)로 끝나면서 접미보다 긴 미등록 토큰
2. 알려진 소재명으로 끝나는 미등록 토큰 (`modacrylic`은 `acrylic`이 아니다)
3. 명시 어휘: 부정 수식어(`faux` `인조` `합성` 등)와 가격 불가 섬유(`metallic` 등)

"미등록 토큰이면 무조건 차단"은 채택하지 않았다. 저장된 실사진 OCR 캐시로 재보니
조성 행 475개 중 92개(19%)가 차단됐고, 대부분 국가명·관리문구·다국어 소재명이라
인식 범위만 깎였다. 좁힌 규칙은 같은 475행 중 1행에서만 반응했고 그 1건은 실제
별칭 누락(`彈性纖維`)이어서 별칭으로 해결했다.

## D-03 氨纶·폴리우레탄은 매핑을 바꾸지 않고 모호성 판정에서만 같은 섬유로 본다

- 날짜: 2026-09-18
- 상태: 적용됨 (`apps/text/rules.py`의 `EQUIVALENT_MATERIALS`)
- 관련: AI 파트 메모 2026-09-16 5절 질문 1

다국어 라벨은 같은 탄성 섬유를 언어마다 `polyurethane` / `폴리우레탄` / `氨纶`으로
쓴다. 지금까지는 이 표기 차이가 서로 다른 조성 후보로 갈려 라벨 전체가
`ambiguous_composition`으로 실패했다 (실제 사례: `QA036.jpg`).

`氨纶`을 어느 키로 통일할지는 정하지 않았다. 대신 모호성 판정에서만 두 키를 같은
섬유로 취급하고, 출력은 각자의 키를 유지한다.

이유: 백엔드 탄소계수가 `spandex` 12.0, `polyurethane` 12.0으로 동일해 어느 쪽을
골라도 계산 결과가 같다. 정식 명칭 통일은 브랜치 병합 시 팀이 정한다.
`ksw/ai-ocr-enhancement`는 `氨纶` 매핑 자체가 없어 맞출 기준이 되지 못한다.

## D-04 부위 마커 방향과 같은 줄 부가 정보 처리

- 날짜: 2026-09-19
- 상태: 적용됨 (`apps/text/parse_label.py`)

- 부위 마커는 기본적으로 뒤따르는 줄을 가리킨다. 라벨이 조성 줄로 시작하고
  단독 마커로 끝날 때만 마커가 앞 줄을 가리키는 것으로 읽는다
  (`100% COTTON SHELL / 100% POLYESTER LINING`).
- 다음 마커 전까지 자기 조성 줄이 없는 겉감 마커는 바로 앞 줄을 가리킨다.
  다른 부위 마커에는 이 추론을 쓰지 않는다. `배색`처럼 조성이 빠진 마커가
  대표 소재 줄을 가져가면 안감이 옷 전체 소재로 확정될 수 있기 때문이다.
- 모든 소재가 명시적 `%`와 짝을 이루는 줄은 품번·제조국·연도·치수가 같은 줄에
  있어도 버리지 않는다. `%` 없는 숫자는 같은 줄에 세탁 문구가 있으면 비율로
  추정하지 않는다.

첫 구현은 "조성 줄이 마커보다 먼저 나오면 후행 마커"로만 판정해,
`면 100% / 안감 / 폴리 100%`의 겉감을 안감으로 잘못 옮겼다. 수정 전 코드와
323개 레이아웃을 차등 비교해 발견했고, 위 규칙으로 회귀 0건을 확인했다.

## D-05 Python 의존성은 실행 범위별로 버전을 잠근다

- 날짜: 2026-09-23
- 상태: 적용됨 (`AI/kdpp_ai_ocr_integrated/requirements-*.lock`, `.github/workflows/ai-checks.yml`)

`requirements*.txt`와 `BACKEND/requirements.txt`는 허용 범위를 적는 입력으로 유지한다.
Python 3.12의 실제 설치는 `uv==0.12.18`로 해석한 정확한 버전의 잠금 파일을 사용한다.
텍스트 OCR은 `requirements-text.lock`, 세탁기호 실험은 `requirements-symbol.lock`,
AI·백엔드 통합 CI는 `requirements-ci.lock`을 사용한다. 심볼 잠금은 기존 실험의
재현성을 위한 것이며 세탁기호 기능 채택이나 서비스 활성화를 뜻하지 않는다.

CI는 세 잠금 파일이 입력 요구사항과 일치하는지 재해석해 비교한 뒤 통합 잠금으로
설치한다. 의존성 변경 시 관련 잠금을 함께 갱신하고 테스트한다. 현재 잠금은
패키지 버전을 고정하며 플랫폼별 배포 파일 해시는 고정하지 않는다.
