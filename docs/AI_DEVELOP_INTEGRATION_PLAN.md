작성일: 2026-10-09 / 공유판 갱신: 2026-10-10

담당: AI는 사용자 측, 프론트엔드·백엔드·DB 연동은 준원
문서 상태: develop 연동 협의안. 아래 제안은 develop에 적용되었다고 확인한 상태가 아니다.

2026-10-10 조회한 develop HEAD는 `3bb58c468c5d0857acfea8e178c7b043a8fc53b8`이다.

아래 자동·HTTP 검사는 2026-10-09와 그 이전 develop 기준이다. 최신 develop 전체 검사로 읽지 않는다.
kyh/ai의 기존 백엔드에는 메타데이터 연결이 이미 있으나, 준원의 develop 통합 기준과는 구분한다.

## 1. 작업 원칙과 코드 기준

AI는 K-DPP-IN의 최신 작업 코드를 유지하고, 프론트엔드와 백엔드는 develop의 코드를 사용한다.
프론트·백엔드에 필요한 변경은 준원이 담당 브랜치에서 수정·검증한 뒤 develop에 반영한다.
통합 담당은 그 develop 버전을 가져와 AI와 다시 검증한다.

| 대상 | 기준 | 주의할 점 |

| AI 원본 | IN 원본 작업 트리 | HEAD는 3b1f6e8이지만 미커밋 변경 41개가 포함된 작업 트리가 기준이다. HEAD만 가져오면 최신 작업을 놓친다. |
| AI 게시 작업 공간 | kyh/ai 작업 트리 | kyh/ai, be12888. IN과 핵심 AI 코드·테스트는 기능상 동일하다. 이번 게시에 QA 인증·실패 분류를 추가했다. |

앞선 검증 당시 BACK의 AI·QA 124개 파일과 IN 원본 해시가 일치했다.
검증 과정에서 IN 원본을 develop 코드로 덮어쓰지 않는다.
프론트·백엔드 담당이 모두 준원이므로 API와 화면 동작을 한 번에 협의한다.

## 2. 확인된 사실과 합의할 사항

### 2.1 배포 검사 호환 오류 — 우선 해결

- BACKEND/check_ai_wiring.py는 ocr_text.Image의 존재로 Pillow 설치 여부를 판단한다.
- 현재 AI는 Pillow를 ocr_image.py에서 사용하므로 ocr_text.Image는 없다.
- Pillow 12.3.0 설치와 실제 이미지 전처리 성공을 확인했지만, 배포 검사는 Pillow 미설치로 실패했다.
- BACKEND/Dockerfile도 이 검사를 실행하므로 이미지 빌드를 막을 수 있다. 실제 Docker 빌드는 실행하지 않았다.
- 준원에게 현재 AI 구조에 맞는 검사로 수정하도록 요청한다. 패키지 재설치만으로 해결되는 문제가 아니다.

### 2.2 AI·백엔드 응답 계약 차이 — 정책 합의 후 수정

- 2026-10-09 이전 develop 기반 AI 연결 검사: 12개 중 5개 통과, 7개 실패. 최신 develop에서 재실행하지 않았다.
- 실패는 독립된 버그 7개가 아니라 연결 함수·배포 검사·메타데이터·실패 응답 정책 차이에 걸쳐 있다.
- 현재 develop의 문자열 OCR 경로에서는 AI의 신뢰도·경고·판정 근거가 API에 보존되지 않는다.
- 소재 조성 충돌이나 미확정 상태도 문자열 OCR에서 예외가 나면 백엔드가 502로 변환한다.
- IN 테스트는 메타데이터 보존과 소재 판정 실패 422를 기대한다.

신뢰도·판정 근거 필드 추가는 현행 develop 계약에 대한 확장 제안이다.
기존 계약에 없는 필드가 빠졌다는 이유만으로 백엔드의 독립적인 결함이라고 단정하지 않는다.
공식 계약을 합의한 뒤 구현과 테스트를 함께 맞춘다.

### 2.3 불완전한 혼용률 — 안전한 실패를 추천

- 예: COTTON 50% POLYESTER 30%.
- IN AI는 합계가 불완전한 조성을 거절하고 확정 소재를 빈 값으로 반환한다.
- 앞선 develop 백엔드 테스트는 부분 인식 200과 ai_success: false를 기대했다. 최신 테스트 전체는 재확인 대상이다.
- 앞선 develop 프론트 ScanApiService는 ai_success를 직접 검사하지 않았다. 최신 화면·모델 동작은 다시 확인한다.

추천안은 422 + MATERIAL_EXTRACTION_FAILED로 직접 입력을 유도하는 것이다.
200 부분 인식 정책을 유지하기로 한다면 프론트에서도 ai_success: false 처리와 화면 동작을 확인해야 한다.
테스트를 통과시키기 위해 AI가 누락 비율을 추측하거나 100%로 보정하도록 바꾸지 않는다.

### 2.4 DB와 실행 환경 — 코드 결함과 구분

- develop의 PostgreSQL·Alembic 구조를 사용한다. IN의 SQLite 구조를 develop에 섞지 않는다.
- 앞선 분리 환경에서는 가입·로그인·탄소 계산·이력 조회가 정상 동작했다. 이전 develop 기준 결과다.
- 최근 점검에서는 검증용 PostgreSQL과 백엔드 포트에 접속되지 않았다.
- 이 상태만으로 DB 설계나 연결 코드의 결함이라고 판단할 수는 없다.
- 최신 develop으로 맞춘 뒤 검증용 DB 기동, 환경변수, 마이그레이션을 확인하고 다시 시험한다.
- 기존 IN DB와 사용자 데이터를 변경하지 않는다. 백엔드 테스트는 별도의 테스트 전용 DB에서 실행한다.

### 2.5 Git·의존성 전달 — 게시 전 확인

- BACK의 공통 Git 제외 규칙인 *.lock 때문에 AI requirements-ci.lock과 requirements-text.lock이 제외된다.
- 실행에 필요한 파일이 로컬에는 있어도 게시 시 누락될 수 있다.
- AI 담당은 코드·테스트·설정·문서·잠금 파일의 전달 목록을 확인한다.
- 자격증명, 실제 DB, 원본 사진, OCR 캐시, 모델·실행 생성물은 코드 게시 대상과 분리한다.
- 이번 kyh/ai 커밋·푸시는 사용자 요청 범위다. develop 병합은 별도 요청과 검토 후 진행한다.

## 4. API 계약 협의안

### 4.1 기존 흐름 유지

- 사진 업로드는 multipart/form-data의 image 필드를 사용한다.
- /api/scan은 소재·혼용률을 반환한다. 탄소 계산과 이력 저장은 이 단계에서 하지 않는다.
- 무게를 정한 뒤 별도 /api/carbon/calculate에서 계산·이력 처리를 한다.
- 기존 materials, material_details, care_instruction, raw_ocr_preview, title, category 등의 필드를 유지한다.
- AI 내부 status: failed와 백엔드 status: error는 다르다. AI 응답을 그대로 내보내지 않고 기존 백엔드 오류 구조로 변환한다.

### 4.2 성공·실패 처리 추천안

아래 표는 합의할 추천안이며 전부 구현되어 있다는 뜻이 아니다.

| 상황 | 응답 | 프론트 처리 |
| --- | --- | --- |
| AI 규칙으로 소재·혼용률 확정 | 200, ai_success: true | 소재와 관리 지침 표시, 사용자 확인 후 다음 단계 |
| 소재 누락·충돌·불완전한 조성 | 422, MATERIAL_EXTRACTION_FAILED | 직접 입력으로 전환, 미확정 값을 확정 결과로 사용하지 않음 |
| Vision 통신·서비스 처리 실패 | 502, OCR_FAILED | 재시도 또는 직접 입력 안내 |
| 로그인 만료·인증 필요 | 401, AUTH_REQUIRED | 기존 세션 만료·재로그인 흐름 |
| 사용자 하루 스캔 상한 | 429, SCAN_DAILY_LIMIT | 제한 안내와 직접 입력 |
| 서버 전체 하루 스캔 상한 | 503, SCAN_UNAVAILABLE | 제한 안내와 직접 입력 |
| AI 모듈 로드 실패 | 503, AI_MODULE_FAILED | 서비스 문제 안내, 운영 측 모듈 연결 점검 |

503은 원인이 둘 이상이므로 필요한 경우 HTTP 상태와 error_code를 함께 본다.
현재 앱은 422와 502 모두 직접 입력을 안내하므로, 상태 코드 차이가 모든 화면 동작을 막는다는 뜻은 아니다.
429의 전용 안내는 현재 일반 실패 안내를 개선하는 제안이다.

### 4.3 추가 메타데이터 추천안

| 필드 | 용도 | 합의할 내용 |
| --- | --- | --- |
| warnings | 인식 과정의 주의 사항 | API 보존 여부와 앱에 보여줄 항목 |
| confidence | OCR·파서 신뢰도 등급 | API 보존 여부와 앱 표시 여부 |
| parse_evidence | 소재·부위·비율 판정 근거 | 진단·검증용 보존 범위 |
| ocr | 후보·호출·처리 결과 메타데이터 | 운영·검증용 보존 범위 |

현재 프론트 모델은 위 네 필드를 읽지 않는다. 백엔드에 필드를 추가하는 것만으로 화면에 표시되지는 않는다.
추천은 API에 근거를 보존하되, 화면에는 합의한 경고만 선택적으로 표시하는 것이다.
신뢰도 등급을 검증되지 않은 확률이나 정확도 퍼센트로 표시하지 않는다.
내부 예외 원문·자격증명·인증 파일 위치는 API나 공유 자료에 포함하지 않는다.

## 5. 준원에게 전달할 메시지

아래 문구를 그대로 전달하고 필요한 범위를 협의할 수 있다.

> AI는 K-DPP-IN의 현재 작업 코드를 기준으로 연결하고 싶습니다. 기존 실사진 평가 대상 48장 중 41장, 85.42%를 확인했고 현재 BACK에도 같은 AI 코드가 들어 있습니다.
>
> 프론트·백엔드와 DB 구조는 develop을 그대로 사용하겠습니다. 현재 BACK은 이전 develop 기준이라, 준원님이 필요한 변경을 담당 브랜치에서 검증한 뒤 develop에 반영해 주시면 그 버전으로 다시 통합하겠습니다.
>
> 우선 check_ai_wiring.py가 현재 AI 모듈 구조 때문에 Pillow 미설치로 잘못 실패하는 부분을 확인해 주세요. Pillow 설치와 실제 전처리는 정상입니다.
>
> AI 연결은 run_ocr_with_metadata와 analyze_ocr_result를 사용하는 방안을 검토해 주세요. 기존 프론트 응답은 유지하면서 신뢰도·경고·판정 근거를 보존하는 방향을 추천합니다. 앱에 어떤 내용을 표시할지는 같이 정하면 좋겠습니다.
>
> 소재 판정 실패는 422, Vision 처리 실패는 502로 구분하고 싶습니다. 합계가 불완전한 혼용률도 422로 직접 입력을 유도하는 방향을 추천합니다. 200 + ai_success: false를 유지한다면 프론트에서도 이를 확정 성공으로 처리하지 않는지 확인 부탁드립니다.
>
> PostgreSQL 마이그레이션과 최신 이메일 인증 흐름을 포함해 로그인 → 스캔 → 직접 입력/결과 확인 → 탄소 계산 → 이력 조회까지 같이 검증하고 싶습니다. 코드 기준과 API 정책을 먼저 맞춘 뒤 저장 OCR 검사, 마지막으로 실사진 검사를 진행하면 좋겠습니다.

## 6. 진행 순서와 완료 조건

1. **기준 고정:** IN의 전달 대상과 develop 커밋을 기록한다. AI는 미커밋 작업을 포함한 파일 기준을 남긴다.
2. **계약 합의:** 부분 인식 처리, 오류 코드, 메타데이터 보존, 앱 표시 범위를 확정한다.
3. **담당자 수정:** AI는 AI 담당이, 프론트·백엔드는 준원이 수정한다. 준원의 변경은 develop에 반영한다.
4. **BACK 통합:** IN AI를 보존하고 합의한 develop 버전으로 프론트·백엔드를 맞춘다.
5. **자동 검사:** AI 검사, 합의한 연결 계약 검사, PostgreSQL 백엔드 전체 테스트, Flutter 분석·테스트, 배포 검사·이미지 빌드를 확인한다.
6. **API·화면 검증:** 최신 가입·이메일 인증·로그인, 스캔, 실패 후 직접 입력, 무게 입력, 탄소 계산, 이력 조회를 확인한다.
7. **저장 OCR 재생:** 기존 사진·캐시를 보존하면서 조합 변경에 따른 판정 퇴행과 응답 구조를 확인한다.
8. **실사진 검사:** 호출 횟수·비용을 합의한 뒤 실제 Vision으로 검증한다. 기존 사진 재검사와 독립 새사진 평가를 구분한다.

실사진 50장을 검사할 경우 최신 develop의 계정당 하루 20회 제한을 반영해 검증용 계정에 나눠 진행한다.
예: 세 계정에 20장·20장·10장. 서버 전체 하루 상한도 사전에 확인한다.
스캔 요청 한 번과 Vision RPC 한 번은 다르므로 각각 집계한다.
하루 제한 자체는 모의 OCR로 검사해 불필요한 유료 호출을 줄인다.

최종 통합본으로 판단할 완료 조건:

- [ ] 준원이 반영한 develop 커밋과 AI 전달 파일 기준이 기록되어 있다.
- [ ] 배포 검사 호환 오류가 해결되고 실제 이미지 빌드가 통과한다.
- [ ] 합의한 API 계약과 관련 테스트가 일치한다. 안전한 실패 규칙을 유지한다.
- [ ] 별도 PostgreSQL에서 마이그레이션과 백엔드 테스트가 통과한다.
- [ ] Flutter 검사와 실제 앱의 정상·실패·직접 입력 흐름을 확인한다.
- [ ] 가입·로그인·탄소 계산·이력 연동이 정상 동작한다.
- [ ] 기존 평가 대상 48장의 41개 정답 기준에서 퇴행과 성공 오답을 확인하고, 결과를 보고한다.
