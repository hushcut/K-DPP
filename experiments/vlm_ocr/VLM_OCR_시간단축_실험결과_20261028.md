- 서비스가 최종으로 고른 후보는 원본 사진의 Vision 원문(text)이고, 그것만 파싱하면 정답과 일치합니다.
- 같은 Vision 응답의 단어 좌표로 줄을 다시 만든 layout 후보는 실패합니다. 기울거나 휘어진 사진에서 단어가 다른 줄에 붙기 때문입니다. 예를 들어 원문에서 한 줄에 있던 비율과 소재명이 layout에서는 서로 다른 줄로 갈라지고, 소재명은 옆 줄의 세탁 문구 단어와 한 줄로 붙습니다.
- 서비스는 모든 후보의 거절 근거를 최종 판정에 넘깁니다(`apps/text/ocr_candidates.py`의 `find_rejected_composition_parts`). 다른 후보로 풀어 주는 것은 "소재에 비율 짝이 없음"(`unpaired_material_rows`)뿐입니다. "근거 오류"(`invalid_composition_evidence`)나 "해석 못 한 소재"(`unresolved_material_token`)는 그대로 남아 맞는 결과를 막습니다.
- 8장은 원본·전처리·소재 영역 등 layout이 아닌 후보 3~5개가 모두 같은 정답 조성을 읽었습니다.
- QA038 한 장은 원본 원문 하나만 성공하고 소재 영역 후보도 실패했습니다. 이 경우는 거절에 근거가 있습니다.

**규칙을 바꾸면 어떻게 되는지 추정** (서비스 파일은 수정하지 않고, 분석 프로세스 안에서만 규칙을 바꿔 다시 돌림)

| 규칙 | 조성 맞힘 | 성공 오답 | 바뀐 사진 |
|---|---:|---:|---|
| 현재 규칙 | 35/89 | 0 | — |
| layout 후보 때문에만 생긴 부위 거절은, layout이 아닌 성공 후보 2개 이상이 같은 조성을 읽었으면 무시 | **42/89** | 0 | +7, 잃은 사진 0 |
| layout 후보의 거절 근거를 모두 무시 | 43/89 | 0 | +9, 잃은 사진 1(QA084) |

- 원인을 찾은 사진과 같은 QA 89장으로 효과를 잰 값이라 낙관적인 추정입니다.
- 서비스에 반영하려면 DJ 50장, 변형 200장, 서비스 테스트에서 성공 오답이 늘지 않는지 먼저 확인해야 합니다.
- 서비스 코드는 K-DPP-AI 담당 범위라 이번에 수정하지 않았습니다.

## 5. 판단

1. **시간:**
   - Vision 서비스는 사진당 최대 6.5초로 89장 모두 10초 안에 끝났습니다.
   - 이 노트북 CPU에서 PaddleOCR-VL 25만 화소는 전체 25초 기준에 모두 들어왔지만, 원본 10초 기준은 약 3분의 2만 통과했습니다.
   - GLM은 10초 기준을 한 장도 통과하지 못했습니다.
2. **정확도:**
   - DJ에서는 서비스 Vision(43/48)이 GLM(25/48)보다 크게 앞섭니다.
   - QA에서는 GLM(39/89)이 서비스(35/89)보다 4장 많이 맞혔습니다. 같은 파서 조건으로는 Vision 원문이 43/89입니다.
   - 137장 합계는 서비스 78장, GLM 64장입니다.
3. **결론:** 합계 정확도와 처리 시간 모두에서 Vision 서비스가 앞서므로 현재 서비스는 Vision 유지가 타당합니다. 무료 모델을 다시 검토하려면 아래 두 가지가 먼저 필요합니다.

   - GPU 서버에서 시간 측정하기

## 6. 한계

- 처리 시간은 이 노트북(Intel Core Ultra 7 155H, CPU만 사용) 기준 참고치입니다. 같은 설정에서도 사진마다 토큰당 시간이 최대 약 2배 다릅니다(발열·전원 관리 추정). 배포 장비에서는 다시 재야 합니다.
- 서비스의 10초·25초 제한은 Vision 후보 호출 기준입니다. 로컬 모델 한 번 호출에 그대로 적용한 것은 이 실험의 비교 기준입니다.
- 4-3과 4-4의 사후 탐색은 저장 출력을 다시 토큰화해 자른 추정입니다. 실제 생성 토큰과 몇 개 차이가 날 수 있습니다.
- 마감 방식은 끊긴 출력도 파싱하는 정책입니다. 이번 자료에서 성공 오답은 0건이었지만, 새 사진에서도 0건이라는 보장은 아닙니다.
- QA 정답지는 대표 조성만 있어 부위 일치는 평가하지 않았습니다.

스크립트(`experiments/vlm_ocr/scripts/`):

- `run_images.py`: 해상도 상한(`--max-pixels`), 반복 감지(`--loop-guard`), EXIF 회전(`--exif-transpose`) 옵션을 추가했습니다.
- `evaluate_batch.py`: 결과 폴더 여러 개를 쉼표로 묶어 평가합니다. 바꾸기 전과 평가 결과가 같은지 확인했습니다.
- `build_qa_set.py`: QA 목록·정답·Vision 캐시 텍스트를 만듭니다(서비스 가상환경에서 실행).
- `simulate_token_cap.py`: 저장 출력을 잘라 출력 상한을 모의 평가합니다.

예시(QA 실행·평가, `experiments/vlm_ocr`에서 Git Bash 기준):

```bash
./venv/Scripts/python.exe -I -X utf8 scripts/run_images.py --model glm --photos /c/K-DPP-AI/QA_DATASET/real_qa_163/images --input-manifest results/qa89_set_20261028_01/manifest.json --exif-transpose --max-pixels 501760 --loop-guard --max-new-tokens 128 --output results/<새 폴더>
```

```bash
/c/K-DPP-AI/AI/kdpp_ai_ocr_integrated/.venv/Scripts/python.exe -I -X utf8 scripts/evaluate_batch.py --manifest results/qa89_set_20261028_01/manifest.json --core-truth results/qa89_set_20261028_01/core_truth.json --graded results/qa89_set_20261028_01/graded.json --photos /c/K-DPP-AI/QA_DATASET/real_qa_163/images --service-dir C:/K-DPP-AI/AI/kdpp_ai_ocr_integrated --run vision=results/qa89_set_20261028_01/vision_original --run glm=results/<새 폴더> --output results/<새 평가 파일>.json
```

출력이 상한에 닿거나 반복 감지로 멈춘 사진이 있으면 `run_images.py`는 종료 코드 1로 끝납니다. 이것은 정상입니다.
