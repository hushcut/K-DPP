# GLM-OCR·PaddleOCR-VL 최종 설정 QA 확인 (5단계)

작성: 2026-11-04 · 작성자: 김요한 · 기준: `kyh/new-ocr`, 서비스 코드 `c49205c`(복사본 사용) · 범위: QA 89장. 설정은 DJ에서 고른 뒤 QA에서 한 번 확인했습니다.

## 1. 요약

- **질문:** DJ에서 고른 무료 VLM 설정이 QA에서도 유효한지, Vision과의 격차가 어떤지 확인했습니다.
- **결과(조성 정답 수):**

| 설정 | DJ 48장 | QA 89장 | 합계 137장 | 틀린 성공 |
|---|---:|---:|---:|---:|
| Vision 서비스 (개선 브랜치 규칙) | **44** | 42 | **86** | 0 |
| Vision 서비스 (현재 코드) | **44** | 35 | 79 | 0 |
| Vision 원본 글자 | 36 | **43** | 79 | 0 |
| PaddleOCR-VL 표 인식 + 자름 | 25 | 42 | 67 | 0 |
| GLM-OCR 전체 사진 | 25 | 39 | 64 | 0 |
| GLM-OCR 기본 + 자름 | 22 | 42 | 64 | 0 |
| GLM-OCR `format2` + 자름 | 23 | 38 | 61 | 1 |
| PaddleOCR-VL 기본 + 자름 | 21 | 39 | 60 | 0 |
| PaddleOCR-VL 전체 사진 | 18 | 31 | 49 | 0 |
| PaddleOCR-VL 표 인식 전체 사진 | 18 | 30 | 48 | 0 |
| PaddleOCR 기본 | 10 | 20 | 30 | 0 |

- **QA 정확도만으로는 Vision의 우위를 말할 수 없습니다.** 무료 최고 설정 42장은 Vision 개선 규칙 42장과 같고, 원본 글자 43장과 1장 차이입니다.
- **격차는 DJ에 남아 있습니다.** 전송으로 작아진 DJ 사진에서는 무료 최고 설정도 25장이고 Vision은 36~44장입니다. Vision 개선 규칙이 실패한 DJ 4장은 어떤 무료 설정도 맞히지 못했습니다.
- **시간은 차이가 큽니다(이 노트북 CPU, 전원 연결).** 무료 최고 경로는 영역을 찾은 62장 기준 사진당 중앙값 26.4초이고, 10초 안에 끝난 사진이 없으며 25초 안은 24장입니다. Vision 서비스는 중앙값 3.3초, 최대 6.5초입니다. GPU 속도는 재지 않았습니다(6·8단계).
- **QA 128토큰 상한은 정답 수에 영향이 없었습니다.** 상한을 없애도 맞힌 사진이 그대로입니다.
- **보고서의 근거를 바꿔야 합니다.** "Vision이 더 정확하다"가 아니라 낮은 해상도에서의 안정성, 시간, 운영 부담을 근거로 삼고, 비용은 8단계에서 함께 따져야 합니다.

## 2. 실험 방법

| 항목 | 내용 |
|---|---|
| 사진 | QA 89장. 1단계와 같은 목록과 정답표. 실제 독립 라벨은 약 43개 |
| 모델 설정 | DJ와 같음. GLM-OCR 50만 화소, PaddleOCR-VL 25만 화소, CPU 8스레드, 반복 감지, 출력 상한 1,024토큰, EXIF 회전 적용 |
| 평가 | `parse_label(text)`와 정답표의 소재·비율 일치(허용 오차 0). 틀린 성공은 파서 성공인데 정답과 다른 경우 |
| 자른 입력 | PaddleOCR 좌표 소재 영역 + 기울기 보정(5도 이상). 2단계 QA 캐시의 원본 후보 좌표만 사용 |
| 못 찾은 사진 | 같은 프롬프트의 전체 사진 결과로 대신해 89장 모두 채점 |
| 표 출력 | `prompt_output_to_text.py`로 글자 줄로 바꾼 뒤 채점 |
| 새 호출 | Vision 0회. Vision 수치는 2단계에서 저장한 값 |
| 시간 | 전원 기록과 파일 시각을 맞춰 **전원 연결·활성 구간의 사진만** 사용 |

- **영역:** QA 62/89장에서 찾았습니다. 면적 비율 중앙값은 15.6%이고 19장을 돌렸습니다. 표본 12장을 눈으로 확인했습니다.
- **스크립트 수정:** `c49205c`의 `validate_image_bytes`는 QA(MPO) 사진에서 회전 전 크기를 돌려줍니다. 좌표와 내용은 회전 후 기준이라 `make_region_crops.py`가 회전 후 크기를 쓰도록 고쳤습니다. DJ 자른 이미지는 3단계와 해시까지 같습니다.
- **재실행의 일치:** 전원 상태가 다른 재측정에서도 글자가 모두 같았습니다(PaddleOCR-VL 전체 사진 89/89, 표 인식 + 자름 62/62, 표 인식 27/27). 11-03에 중단했다가 11-04에 이어 읽은 실행도 정답 수에 영향이 없습니다.

|---|---:|---:|---:|---|---:|---:|

| GLM-OCR `format2` + 자름 | 38 | 21 | 17 | — | 1 | — |
| PaddleOCR-VL 전체 사진 | 31 | 17 | 14 | — | 0 | — |

- `format2`의 틀린 성공 1건은 영역을 못 찾아 전체 사진으로 읽은 사진입니다. DJ에서도 형식 지정 프롬프트에서 같은 위험이 나타났으므로 후보에서 뺍니다. 자른 62장만 봐도 전체 사진 24장보다 적은 21장입니다.
- `format2`는 대체 결과가 27장뿐이라 62장과 27장을 따로 채점해 더했습니다.
- PaddleOCR은 새 실행(전원 연결)도 20장으로 1단계와 같습니다.

### 3.2 128토큰 상한의 영향

1단계 QA 수치는 128토큰 상한 실행이라 GLM-OCR 45장, PaddleOCR-VL 38장이 잘린 값입니다. 상한을 1,024토큰으로 올려 다시 돌렸습니다.

| 모델 | 128토큰 raw / strict | 1,024토큰 raw / strict | 달라진 사진 | 상한·반복 중단 |
|---|---:|---:|---:|---:|
| GLM-OCR | 39 / 28 | 39 / 39 | 0 | 45 → 1 |
| PaddleOCR-VL | 31 / 28 | 31 / 31 | 0 | 38 → 9 |

1단계의 raw 수치는 그대로 유효합니다. 조성이 앞쪽 128토큰 안에 들어온 사진에서 정답이 결정된 것으로 보입니다.

### 3.3 자르기 효과: DJ와 QA

| 설정 | DJ 전체 → 자름 | QA 전체 → 자름 |
|---|---:|---:|
| GLM-OCR 기본 | 25 → 22 | 39 → 42 |
| PaddleOCR-VL 기본 | 18 → 21 | 31 → 39 |
| PaddleOCR-VL 표 인식 | 18 → 25 | 30 → 42 |

3단계의 가설대로 사진이 큰 QA에서 효과가 더 큽니다. QA 사진(약 1,220만 화소)을 줄이면 가로세로가 GLM-OCR 약 0.20배, PaddleOCR-VL 약 0.14배입니다. 자른 이미지(중앙값 약 241만 화소)는 약 0.46배, 0.32배라 같은 입력 크기에서 글자가 약 2.2배 크게 들어갑니다(계산값).

### 3.4 Vision과 서로 보완하는가

| 무료 설정 | QA: Vision 개선 규칙 실패 47장 중 정답 | QA: Vision만 정답 | QA 합집합 | DJ: Vision 개선 규칙 실패 4장 중 정답 | DJ: Vision만 정답 | DJ 합집합 |
|---|---:|---:|---:|---:|---:|---:|

- QA에서는 두 쪽이 서로 다른 사진을 맞힙니다. Vision 실패 시 무료 경로를 쓰면 42장에서 53장이 되는 셈입니다. 답을 아는 합집합이지만, 이번 후보들의 틀린 성공이 0건이라 파서 성공만 쓰는 규칙에서도 비슷할 것으로 보입니다. 실제 순서형 규칙으로 돌려 보지는 않았습니다.
- DJ에서는 보완이 없습니다.
- 참고로 현재 코드의 Vision 서비스(35장) 기준으로는 실패 54장 중 14장을 맞혀 합집합 49장입니다. 원본 글자(43장) 기준으로는 실패 46장 중 11장을 맞혀 합집합 54장입니다.

## 4. 관찰

### 4.1 사진 품질이 격차를 가르는 것으로 보입니다
무료 VLM은 큰 원본 사진을 잘라 글자를 크게 넣어 주면 Vision에 근접하고, 이미 작아진 DJ 전송본에서는 크게 뒤처집니다. DJ·QA는 사진 종류 외에 라벨 구성도 다르므로 해상도만의 효과로 단정하지는 않습니다. 같은 QA 사진을 DJ 수준으로 줄여 비교한 적은 없습니다.

### 4.2 서비스 판정 규칙의 영향
같은 Vision에서 QA 정답이 현재 코드 35장, 개선 규칙 42장, 원본 글자 43장으로 다릅니다. 무료 경로는 후보 하나의 글자를 파서로 읽는 단순한 구조인데, Vision 서비스는 여러 후보와 좌표를 함께 판정합니다. QA에서 Vision 서비스의 정답이 원본 글자보다 적은 것은 엔진이 아니라 판정 규칙 때문입니다(1단계 분석).

### 4.3 표 인식의 위험
전체 사진 표 인식은 출력 상한·반복 중단이 20장으로 기본(9장)보다 많고 정답도 30장으로 늘지 않습니다. 자른 입력에서만 효과가 있습니다. QA와 DJ에서 틀린 성공은 없었지만, DJ 소수 시험에서 행이 밀린 사례가 있어 표본이 커지면 나타날 수 있습니다(`VLM_OCR_프롬프트_실험결과_20261103.md` 4.3).

### 4.4 무료 경로의 운영 부담
최고 설정을 쓰려면 PaddleOCR 읽기, 서비스 영역 찾기, 기울기 보정, VLM 표 인식, 표 태그 변환, 파서까지 모두 돌려야 하고, 영역을 못 찾으면 전체 사진으로 대체해야 합니다. 모델 두 개를 띄우고 관리해야 합니다.

## 5. 보고서에 쓸 점

1. 큰 원본 사진(QA)에서는 무료 최고 설정 42/89가 Vision 개선 규칙 42/89, 원본 글자 43/89와 사실상 같습니다. QA 정확도를 근거로 Vision을 고른다고 쓰면 안 됩니다.
2. 전송으로 작아진 사진(DJ)에서는 무료 최고 설정 25/48, Vision 36~44/48입니다. Vision은 사진 품질이 나빠져도 덜 흔들립니다. 무료 경로는 Vision이 실패한 DJ 사진을 보완하지 못했습니다.
3. 합계 137장은 Vision 개선 규칙 86장, 무료 최고 설정 67장입니다.
4. 노트북 CPU에서 무료 최고 경로는 중앙값 26.4초로 Vision 서비스 3.3초의 약 8배입니다. 서비스 25초 제한을 62장 중 24장만 지킵니다. GPU에서 달라질 수 있어 6·8단계에서 확인합니다.
5. 무료 최고 설정은 모델 두 개와 여러 단계의 처리가 필요합니다. 공짜인 것은 호출비뿐이고, 서버와 운영 비용을 8단계에서 비교해야 합니다.
6. 형식 지정 프롬프트를 쓰지 않은 설정은 틀린 성공이 0건입니다. 이 설정들은 틀리기보다 찾지 못하고 실패합니다. 형식 지정 프롬프트는 QA `format2` 1건, DJ `format` 5건처럼 틀린 성공을 만듭니다.
7. QA에서는 Vision 실패 사진을 무료 경로가 보완할 여지가 있습니다(47장 중 11장). 다만 답을 아는 합집합이고 시간이 크게 늘어납니다.

## 6. 한계

- QA는 이전 실험에서 Vision 판정 개선에 참고한 사진이고, 독립 라벨은 약 43개입니다. 독립 평가 묶음이 아닙니다. 설정 선택에는 쓰지 않았습니다.
- 서비스 파서는 Vision 출력에 맞춰 개발됐습니다. 무료 엔진에 불리할 수 있습니다.
- 1~2장 차이는 흔들림일 수 있습니다. 같은 라벨을 다시 찍은 사진이 많아 사진 수만큼 독립적이지 않습니다.
- Vision 서비스 수치는 `c49205c`이고, 이 코드는 QA에서 회전 전 크기로 소재 영역을 찾습니다. 저장된 좌표로 계산하면 Vision 영역이 18장에서 달라집니다(새로 찾는 1장 포함). `817a01a`가 고쳤지만 `kyh/ggl-ocr`에는 없고, 정답 수에 미치는 영향은 Vision을 새로 호출해야 해서 재지 않았습니다.
- 시간은 GPU 없는 노트북 CPU 기준이고, 전원 연결 구간도 실행 시점에 따라 달라집니다. 표 인식 + 자름은 전원 연결 구간만 봐도 앞선 실행 40장 중앙값 10.8초, 재측정 62장 12.9초입니다(사진 구성이 달라 바로 비교할 수는 없음).
- Vision 시간은 10-28 실호출로, 네트워크가 포함되고 측정 환경이 다릅니다.
- PaddleOCR-VL 전체 사진 시간은 36장, GLM-OCR 전체 사진 시간은 74장뿐입니다. 전체 경로 시간은 영역을 찾은 62장만 봤으므로 89장 전체는 더 깁니다.
- 전체 경로 시간은 두 측정의 합입니다. 실제로 이어 붙여 돌린 값이 아니고, 영역 찾기와 기울기 보정 시간은 넣지 않았습니다.

## 7. 재현 방법

작업 폴더 `experiments/vlm_ocr/`, Git Bash 기준입니다. 결과 폴더는 항상 새 경로를 지정합니다. 시간을 잴 때는 전원을 연결하고 덮개를 닫지 않습니다.

```bash
# QA 자른 이미지
<서비스 .venv python> -I -B -X utf8 scripts/make_region_crops.py --service-dir <서비스 코드 c49205c> --photos <QA 사진 폴더> \
  --manifest results/qa89_set_20261028_01/manifest.json --ocr-cache <PaddleOCR QA 캐시> --output results/<새 폴더> --deskew

# 자른 입력 읽기(GLM-OCR은 --model glm --max-pixels 501760, 기본 프롬프트면 --prompt 생략)
./venv/Scripts/python.exe -I -X utf8 scripts/run_images.py --model paddle_vl --photos results/<자른 이미지 폴더>/images \
  --input-manifest results/<자른 이미지 폴더>/manifest.json --max-pixels 250880 --loop-guard --prompt "Table Recognition:" --output results/<새 결과 폴더>

# 전체 사진 읽기(이어 읽을 때는 --resume)
./venv/Scripts/python.exe -I -X utf8 scripts/run_images.py --model paddle_vl --photos <QA 사진 폴더> \
  --input-manifest results/qa89_set_20261028_01/manifest.json --exif-transpose --max-pixels 250880 --loop-guard --output results/<새 결과 폴더>

# 표 출력을 글자 줄로 바꾸기
./venv/Scripts/python.exe -I -X utf8 scripts/prompt_output_to_text.py --input results/<결과 폴더> --output results/<새 폴더> --kind table

# 자른 입력 채점(못 찾은 사진은 --base의 전체 사진 결과로 대신)
<서비스 .venv python> -I -B -X utf8 scripts/region_eval.py --service-dir <서비스 코드 c49205c> \
  --manifest results/qa89_set_20261028_01/manifest.json --core-truth results/qa89_set_20261028_01/core_truth.json \
  --graded results/qa89_set_20261028_01/graded.json --base 기준이름=<전체 사진 결과> \
  --crop "이름=<자른 이미지 목록>=<결과 폴더>=기준이름" --output <새 채점 JSON>

# 전원 상태 기록
powercfg //batteryreport //output <임시 폴더>/battery.html
```
