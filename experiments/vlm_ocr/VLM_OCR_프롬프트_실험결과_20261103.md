# GLM-OCR·PaddleOCR-VL 프롬프트와 출력 형식 실험 (4단계)

작성: 2026-11-03 · 작성자: 김요한 · 기준: `kyh/new-ocr`, 서비스 코드 `c49205c`(복사본 사용) · 범위: DJ 48장(설정 조정용). QA 확인은 5단계에서 합니다.

## 1. 요약

- **질문:** 프롬프트와 출력 형식을 바꾸면 무료 VLM의 정확도와 시간이 나아지는지 확인했습니다.
- **결과(DJ 48장, 조성 정답 수 / 틀린 성공):**

| 프롬프트 | 전체 사진 | PaddleOCR 좌표 소재 영역 + 기울기 보정 |
|---|---:|---:|
| GLM-OCR 기본 | **25** / 0 | 22 / 0 |
| GLM-OCR 형식 지정 `format` | 18 / **5** | 21 / 1 |
| GLM-OCR 형식 지정 `format2` | 19 / 0 | 23 / 0 |
| GLM-OCR JSON | 16 / 1 | 실행 안 함 |
| PaddleOCR-VL 기본 | 18 / 0 | 21 / 0 |
| PaddleOCR-VL 표 인식 | 18 / 0 | **25** / 0 |
| 참고: Vision 원본 글자 36 · Vision 서비스 전체 경로 44 | | |

- **GLM-OCR:** 형식을 지정하면 정답이 25장에서 16~19장으로 줄고, 틀린 성공이 최대 5건 생깁니다. 시간은 약 절반으로 줄지만(같은 사진 10장 중앙값 약 23초→11~16초) 쓸 수 없는 설정입니다.
- **PaddleOCR-VL:** 자유 문구는 무시합니다. 표 인식과 자르기를 합치면 18장에서 25장으로 늘어, 이번 단계에서 유일하게 정확도가 오른 설정입니다. 다만 표 태그를 글자로 바꾸는 후처리가 필요하고, 영역을 찾으려면 PaddleOCR을 먼저 돌려야 합니다.
- **Vision과의 격차는 그대로입니다.** 최고 25장으로 Vision 원본 글자 36장, 서비스 전체 경로 44장에 못 미칩니다. Vision 서비스 경로가 실패한 4장은 어떤 설정도 맞히지 못했습니다.
- **시간 측정 문제를 발견했습니다.** 실행 중 노트북이 배터리나 절전 상태로 바뀌면 같은 출력의 시간이 최대 2.5배까지 달라집니다. 글자는 달라지지 않아 **정확도 수치는 유효**하지만, 1~3단계의 시간 수치에도 이 영향이 섞여 있습니다(3.4).

## 2. 실험 방법

| 항목 | 내용 |
|---|---|
| 사진 | DJ 50장 실행, 조성 평가 48장(DJ030·DJ046 제외). 정답표는 1단계와 같음 |
| 모델 설정 | 1단계와 같음. GLM-OCR 50만 화소, PaddleOCR-VL 25만 화소, CPU 8스레드, 반복 감지, 출력 상한 1,024토큰 |
| 평가 | `parse_label(text)`와 정답표의 소재·비율 일치(허용 오차 0). 틀린 성공은 파서 성공인데 정답과 다른 경우 |
| 자른 입력 | 3단계 후보인 PaddleOCR 좌표 소재 영역 + 기울기 보정 36장. 나머지 12장은 같은 프롬프트의 전체 사진 결과로 대신함 |
| 새 호출 | Vision 0회 |

사진 6장으로 먼저 시험해 효과가 없는 문구를 뺐습니다. `format2`와 JSON은 소수 시험 없이 바로 전체를 돌렸습니다.

| 이름 | 모델 | 프롬프트 | 소수 시험 결과 | 전체 실행 |
|---|---|---|---|---|
| 기본 | GLM-OCR | `Text Recognition:` | 기준 | 1단계 결과 |
| `format` | GLM-OCR | `Extract the fiber composition from this clothing label. Write one material per line as: material percent%. Write nothing else. If there is no composition, write NONE.` | 토큰이 크게 줄어듦 | 함 |
| `format2` | GLM-OCR | `Extract the fiber composition from this clothing label. Write one material per line as: material percent%. Keep each material name in the label's language. Write nothing else.` | 소수 시험 안 함. `format`의 소재명 손실을 보완하려는 문구 | 함 |
| JSON | GLM-OCR | `请按下列JSON格式输出图中信息:` 줄바꿈 `{"composition": [{"material": "", "percent": ""}]}` | 소수 시험 안 함. 정보 추출용으로 알고 있는 지시문이며 공식 문서로 확인하지는 않음 | 함 |
| 조성만 읽기 등 3종 | GLM-OCR | 영어·한국어 자유 문구 | 전체 전사 그대로, 토큰이 줄지 않음 | 안 함 |
| 표 인식 | GLM-OCR | `Table Recognition:` | 30~58초로 느리고 조성이 사라진 사진이 있음 | 안 함 |
| 기본 | PaddleOCR-VL | `OCR:` | 기준 | 1단계 결과 |
| 표 인식 | PaddleOCR-VL | `Table Recognition:` | 표 태그로 출력. 행이 밀린 사진이 있어 위험 확인 필요 | 함 |
| 자유 문구 3종 | PaddleOCR-VL | GLM-OCR과 같은 문구 | 기본과 토큰이 같고 일부는 더 나쁨 | 안 함 |

- **PaddleOCR-VL의 자유 문구:** 입력 토큰이 늘어(333→351~394) 프롬프트가 모델까지 전달된 것은 확인했습니다. 전달됐는데도 출력이 그대로이므로 무시하는 것으로 봅니다.
- **출력 변환:** 파서는 글자 줄만 읽으므로 `prompt_output_to_text.py`로 표 태그와 JSON을 줄 글자로 바꿔 새 폴더에 쓴 뒤 채점했습니다. 표 인식 출력은 변환이 필수입니다(변환 전 1장, 변환 후 18장).

전체 실행의 시간이 토큰과 맞지 않아 원인을 찾았습니다. 윈도우 배터리 보고서의 사용 기록과 실행 시각을 맞춰 보니, 일부 실행이 절전(Connected standby)이나 배터리 상태에서 돌았습니다.

| 같은 사진 10장, 같은 출력 | 상태 | 시간 합계(초) |
|---|---|---:|
| GLM-OCR `format` 전체 실행 구간 | 절전 + 전원 연결 | 327.5 |
| GLM-OCR `format` 재측정 | 전원 연결·활성 | 163.1 |

- **정확도는 영향이 없습니다.** 같은 설정을 다시 돌린 8쌍(사진 10장씩, 80건)의 글자가 모두 같습니다. GLM-OCR 기본 앞뒤 1쌍을 뺀 7쌍은 실행 구간의 전원 상태가 다릅니다.
- 그래서 이 문서의 시간 비교는 전원 연결·활성 상태의 측정값만 씁니다.

**GLM-OCR 프롬프트별 시간(같은 사진 10장, 기본→후보→기본 순서로 측정):**

| 프롬프트 | 중앙값 / 최소 / 최대(초) | 10초 이내 | 25초 이내 | 토큰 합 |
|---|---:|---:|---:|---:|
| 기본(앞) | 23.4 / 14.2 / 41.6 | 0 | 5 | 1,428 |
| `format` | 11.4 / 10.5 / 38.8 | 0 | 8 | 693 |
| `format2` | 16.1 / 12.1 / 27.2 | 0 | 8 | 731 |
| JSON | 13.8 / 13.4 / 15.3 | 0 | 10 | 298 |
| 기본(뒤) | 22.2 / 12.3 / 37.2 | 0 | 5 | 1,428 |

- 사진별 시간을 토큰에 맞추면 고정 시간 약 10~13초 + 토큰당 약 0.09초입니다. 출력이 몇 토큰뿐이어도 10.5초가 걸려, **50만 화소 GLM-OCR은 서비스의 원본 10초 제한을 프롬프트로 맞출 수 없습니다.**

**PaddleOCR-VL:** 같은 10장의 전원 연결·활성 측정값은 기본 120.9초(중앙값 11.4초), 표 인식 153.3초(중앙값 13.3초)입니다. 토큰 합이 1,235에서 1,507로 늘어난 것과 비슷하게 약 1.3배 느립니다. 두 측정은 시각이 약 30분 다릅니다. 재측정의 표 인식은 전원이 빠진 뒤라 쓰지 않았습니다.

**자른 입력의 프롬프트 시간은 아직 비교할 수 없습니다.** 세 실행 모두 배터리 상태였습니다(표 인식 + 자름 중앙값 11.0초). 토큰으로 보면 표 인식 + 자름은 기본 + 자름(8.4초, 전원 연결)보다 약간 느릴 것으로 보이며, 전원을 연결하고 다시 재야 합니다.

**1~3단계에 미치는 영향:**

| 측정 | 전원 상태 |
|---|---|
| GLM-OCR·PaddleOCR-VL 기준 실행(10-28) | DJ: GLM-OCR 배터리 + 전원 연결, PaddleOCR-VL 배터리. QA: 배터리·전원 연결·절전 혼재 |
| PaddleOCR·EasyOCR 기본(10-30) | PaddleOCR DJ·QA 배터리, EasyOCR DJ 배터리, EasyOCR QA 혼재 |
| PaddleOCR 서비스 경로(11-02) | 369회 중 전원 연결·활성 249회, 배터리 56회, 절전 64회(끝 시각에서 거꾸로 계산한 추정) |
| 자르기 실행과 PaddleOCR 검출만(11-03, 3단계) | 전원 연결·활성 |

- 3단계의 "자르면 시간이 절반"은 전체 사진 쪽이 배터리 상태여서 과장됐을 수 있습니다. 재측정 10장 기준 전체 사진 시간이 GLM-OCR 약 1.2배, PaddleOCR-VL 약 1.5배 부풀어 있었습니다. 토큰이 절반 이하로 주는 것은 그대로입니다.
- "PaddleOCR이 시간 제한을 지키지 못한다"는 2단계 결론은 유지됩니다. 전원 연결·활성 호출만 봐도 최소 9.5초, 중앙값 17.3초입니다.
- 무료 경로가 전체 사진보다 느리다는 3단계 결론도 유지됩니다. PaddleOCR 검출(전원 연결, 중앙값 17.0초)은 전체 사진 읽기(재측정 PaddleOCR-VL 11.4초)보다 이미 깁니다.

## 4. 관찰

### 4.1 형식을 지정하면 왜 위험한가
- `format`의 틀린 성공 5건은 기본 프롬프트에서 파서가 실패로 막던 사진입니다. 소재명을 깨진 글자나 파서가 모르는 언어로 읽던 라벨에서 그럴듯한 다른 소재명을 적어(4장) 파서를 통과했고, 두 소재를 한 소재 100%로 줄인 경우도 있습니다(1장).
- 읽어 적는 일이 내용을 추측해 채우는 일로 바뀐 것으로 보입니다. 형식이 깔끔해 파서가 걸러 내지도 못합니다. 서비스에서 가장 위험한 실패 유형입니다.
- 소재명을 라벨 언어로 유지하라는 문구를 더한 `format2`는 이번 DJ에서 틀린 성공이 0건입니다. 이 문구의 효과인지는 사진 수가 적어 단정하지 않습니다.

### 4.2 형식을 지정하면 왜 정답이 줄어드는가
직접 본 분류입니다.

| 원인 | `format` 잃은 8장 | `format2` 잃은 8장 |
|---|---:|---:|
| 소재명이나 비율 누락 | 2 | 2 |
| 지시문의 `material percent%`를 그대로 따라 씀 | 3 | 4 |
| 겉감·안감 구분이 사라져 파서가 대표 조성을 못 고름 | 3 | 2 |

마지막 항목은 구조적인 문제입니다. 서비스 파서는 부위 표시로 대표 조성을 고르는데, 조성만 뽑으라는 지시가 그 단서를 지웁니다.

### 4.3 표 인식 + 자르기가 왜 효과가 있는가
기본 + 자름에서 틀렸다가 맞게 된 7장을 직접 본 결과입니다(1장은 영역을 못 찾아 전체 사진으로 대신한 사진). 소재 칸과 비율 칸이 나뉜 라벨에서 일반 읽기는 소재를 먼저 다 적고 비율을 나중에 적거나 소재명을 빠뜨리는데, 표 인식은 행 단위로 소재와 비율을 한 줄에 적는 경우가 많았습니다. 파서가 바라는 형태입니다. 자르면 라벨 밖의 글자가 빠지고 토큰도 줄어듭니다.

위험도 있습니다. 소수 시험에서 행이 한 칸 밀려 비율이 다른 소재에 붙은 사진이 있었습니다. 이번에는 파서가 막아 틀린 성공이 0건이지만, 다른 사진에서는 통과할 수 있습니다. QA에서 틀린 성공을 먼저 봐야 합니다.

## 5. 보고서에 쓸 점

1. 형식을 지정한 프롬프트는 출력을 줄이지만 DJ 정답이 25장에서 16~19장으로 줄고, 틀린 성공이 최대 5건 생겼습니다. 없던 위험이 생기는 설정입니다.
2. PaddleOCR-VL은 자유 문구를 무시해 프롬프트로 조절할 여지가 작습니다. 표 인식과 자르기를 합친 설정만 18장에서 25장으로 올랐습니다.
3. 그 최고 설정도 PaddleOCR 검출(중앙값 17초)과 표 후처리가 필요하고, Vision 원본 글자 36장, 서비스 전체 경로 44장에 못 미칩니다.
4. 50만 화소 GLM-OCR은 출력이 거의 없어도 10초를 넘어, 서비스 시간 제한을 프롬프트로 해결할 수 없습니다.
5. 로컬 모델의 시간은 전원 상태에 민감합니다. 같은 출력이 최대 2.5배 차이 나므로 운영 환경 수치로 쓰면 안 됩니다. 비용 비교(8단계)에는 전원 연결 재측정값을 씁니다.

## 6. 한계

- DJ는 설정 조정에 쓴 사진입니다. 3·4단계에서 같은 48장으로 설정 약 20개를 비교했으므로, 최고값 25장에는 고르는 과정의 이득이 섞여 있을 수 있습니다. 5단계 QA로 확인합니다.
- DJ는 사진이 작고 같은 옷을 다시 찍은 사진이 섞여 있어 2~3장 차이는 흔들림일 수 있습니다.
- JSON 변환은 출력을 본 뒤 기호를 지우는 방식으로 고쳤습니다. 지시문을 따라 쓴 출력은 지우지 않았습니다. 후처리를 더 하면 몇 장 늘 수 있지만, 그만큼 DJ에 맞춘 규칙이 됩니다.
- 시간 재측정은 10장뿐입니다. 2·3단계 문서의 시간 표는 다시 재지 않았습니다.
- 전원 상태는 사용 기록과 파일 시각을 맞춘 값입니다. 절전·배터리와 시간 증가가 함께 나타나는 것은 확인했지만, 내부 작동 원인까지 확인하지는 않았습니다.
- 앞으로 `run_images.py`는 사진마다 전원 연결 여부(`power_plugged`)를 기록합니다. 절전 상태는 기록하지 않습니다.
- 서비스 코드는 `c49205c` 기준입니다. 시간은 GPU 없는 노트북 CPU 기준입니다.

## 7. 재현 방법

작업 폴더 `experiments/vlm_ocr/`, Git Bash 기준입니다. 결과 폴더는 항상 새 경로를 지정합니다. 시간을 잴 때는 전원을 연결하고 절전에 들어가지 않게 합니다.

```bash
# 프롬프트를 바꿔 읽기(PaddleOCR-VL은 --model paddle_vl --max-pixels 250880 --prompt "Table Recognition:")
./venv/Scripts/python.exe -I -X utf8 scripts/run_images.py --model glm --photos <DJ 사진 폴더> \
  --input-manifest results/dj50_manifest_20261028_01.json --max-pixels 501760 --loop-guard --prompt "<프롬프트>" --output results/<새 결과 폴더>

# 표·JSON 출력을 글자 줄로 바꾸기
./venv/Scripts/python.exe -I -X utf8 scripts/prompt_output_to_text.py --input results/<결과 폴더> --output results/<새 폴더> --kind table

# 전체 사진 채점
<서비스 .venv python> -I -B -X utf8 scripts/evaluate_batch.py --manifest results/dj50_manifest_20261028_01.json \
  --core-truth results/dj50_core_truth_20261028_01.json --graded <조성 정답표> --photos <DJ 사진 폴더> --service-dir <서비스 코드 c49205c> \
  --run glm=results/glm_px502k_20261028_01 --run 이름=<결과 폴더> --output <새 채점 JSON>

# 자른 입력 채점(자른 이미지는 3단계 문서의 방법으로 만든다)
<서비스 .venv python> -I -B -X utf8 scripts/region_eval.py --service-dir <서비스 코드 c49205c> \
  --manifest results/dj50_manifest_20261028_01.json --core-truth results/dj50_core_truth_20261028_01.json --graded <조성 정답표> \
  --base 기준이름=<같은 프롬프트의 전체 사진 결과> --crop "이름=results/dj_crops_paddle_deskew_20261103_01/manifest.json=<결과 폴더>=기준이름" --output <새 채점 JSON>

# 전원 상태 기록(어느 구간이 절전·배터리였는지 확인)
powercfg //batteryreport //output <임시 폴더>/battery.html
```
