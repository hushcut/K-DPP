### 3.3 승우 본 학습 (7단계, README 기록이며 재현 전)

- **위치:** `origin/ksw/paddleocr` 최신 `d334c42`(2026-10-25). `kyh/new-ocr`의 `experiments/paddleocr/README.md`에는 이 내용이 없습니다. 보려면 `git fetch origin ksw/paddleocr` 후 `git show d334c42:experiments/paddleocr/README.md`를 씁니다. 브랜치를 바꾸지 않습니다.
- **학습:** 인식 모델만, 학습 1,516줄, 검증 365줄(옷 단위 18묶음, 사진 36장), 10 epoch 중 7번째 선택, CPU 12시간 35분.
- **줄 단위 결과:** 정확 일치 57.5% → 75.9%(210 → 277줄), 띄어쓰기 무시 69.9% → 79.2%, CER 11.2% → 3.9%, 소재 관련 90줄 65.6% → 80.0%. 새로 틀린 줄 18줄.
- **한계:** 조성 판정과 새 사진은 재지 않았습니다. 같은 검증 줄로 epoch를 골라 낙관적일 수 있습니다. 결과 파일, 로그, 모델은 승우 PC에만 있습니다.
- **평가 제약:** 학습에 실사진 06~50과 QA001~163을 썼으므로 **QA 89장과 DJ 48장 전체로 이 모델을 평가하면 안 됩니다.** 검증 묶음이나 새 사진만 씁니다.
- **어긋난 기록(승우 확인 필요):** 25자 제한으로 빠진 학습 줄이 README는 61줄, 10-27 인계 기록은 296/1,516줄입니다. 학습 전 CER도 11.2%와 15.4%로 다릅니다.
- **정답표:** 승우가 의심한 6장 중 QA003, QA041, QA077이 QA 89장에 있습니다. Vision 서비스, Vision 원본, 무료 최고 설정의 결과가 세 장 모두 같아(QA003 정답, 나머지 실패) 격차에는 영향이 없습니다.

### 3.5 운영 부담

무료 최고 경로는 PaddleOCR → 영역 찾기 → 기울기 보정 → PaddleOCR-VL → 표 변환 → 파서 순서이고, 영역을 못 찾으면 전체 사진으로 대체합니다. 모델 두 개와 서버, 대기열, 출력 폭주에 대비한 시간 제한이 필요합니다. 정확도를 개선하려면 라벨 작업(승우는 208장 3,328줄 검토, 확인 필요 694줄 남음)과 학습이 듭니다. 장점은 **사진이 외부로 나가지 않는 것과 사용량에 따른 요금 위험이 없는 것**입니다. 사진을 외부로 보낼 수 없는 요건이 생기면 결론이 달라질 수 있습니다.

## 6. 함정

**측정**
- CPU 시간은 전원 상태에 민감합니다(같은 출력이 최대 2.5배). 재기 전에 전원 연결, 덮개 열림, 절전 방지를 요청하고, 끝나면 전원 기록과 대조합니다. 글자는 전원과 무관하게 같았습니다.
- 다른 날 기록과 비교하지 말고 같은 시간대에 CPU를 다시 잽니다. GLM-OCR 11-03 기록 214.0초와 비교했으면 1.8배로 부풀려질 뻔했습니다(같은 시간대 CPU는 162.6초).
- 프로세스의 첫 사진은 3초 안팎 더 걸립니다.
- 멈출 때는 상위 스크립트까지 확인합니다. 작업 종료 표시 뒤에도 살아 있던 적이 있습니다.

**믿으면 안 되는 값**
- `paddle_vl_qa_missing_table_time_20261104_01`: 27장 전부 배터리 측정입니다.
- `paddle_vl_qa_missing_table_cpu_20261104_01`: 15:13:05에 전원이 빠져 27장 중 15장이 배터리 측정입니다. 글자는 쓸 수 있지만, **VL CPU의 89장 시간은 확정값이 아닙니다.** 다시 재면 약 6분입니다.
- 2026-11-04의 전원 연결 구간은 14:06:10~15:13:05입니다. `qa89_default_20261104_01`과 `paddle_vl_qa_crop_table_time_20261104_01`은 5단계에서 전원 기록과 대조했습니다.

**OpenVINO**
- GPU 기본 정밀도 **f16은 결과가 망가집니다**(181줄 중 22줄 일치). 반드시 `--gpu-precision f32`를 씁니다.
- 인식까지 GPU에 올리면 느립니다(10장 합계 104.1초, 첫 장 50.8초). 입력 폭이 사진마다 달라 다시 컴파일하는 것으로 보이지만 확인하지는 않았습니다.
- GPU 컴파일은 캐시가 없으면 약 40초입니다. 캐시는 `paddleocr/models/onnx/ov_cache`입니다.
- QA040은 검출만 8.2초로 튀었고 원인은 확인하지 못했습니다.
- `run_paddleocr_openvino.py`는 PaddleX의 추론 호출만 바꾸므로 전후처리는 기존 실행과 같습니다.

**설치**
- `paddle2onnx`는 Windows에서 Paddle 3.0.0을 막습니다. 그래서 변환에만 3.1.1을 씁니다. 검사를 우회하지 않습니다.
- `paddle2onnx`는 `packaging`을 의존성으로 선언하지 않아 따로 설치했습니다.
- 변환 중 Polygraphy가 `onnxruntime`, `onnx_graphsurgeon`(NVIDIA 색인 추가), `sympy`를 스스로 설치했고 `numpy`도 2.4.6으로 올렸습니다. 변환 환경에만 있고 실행 환경에는 없습니다.
- `GPUtil==1.4.0`은 소스 배포만 있어 `--only-binary=:all:`과 함께 쓰면 `--no-binary=GPUtil`이 필요합니다.

**스크립트**
- `run_images.py`의 종료 코드 1은 오류가 아닐 수 있습니다. 반복 중단이나 상한 도달 사진이 하나라도 있으면 1로 끝납니다. `summary.json`의 `status`를 봅니다.
- 긴 출력은 내장 그래픽이 CPU보다 느립니다(QA077 내장 그래픽 208초, 배터리 상태 CPU 107~119초).
- 승우의 `15_stage5_compare.py`는 `results/stage5_compare.json`을 덮어씁니다. 먼저 복사합니다.
- Windows PowerShell 5.1의 `ConvertFrom-Json`은 배열을 한 덩어리로 돌려줘 집계가 틀어질 수 있습니다. 집계는 Python으로 합니다.
- `c49205c`의 회전 전 크기 문제는 `817a01a`가 고쳤지만 `kyh/ggl-ocr`에는 없습니다.

**낡은 기록**
- `vlm_ocr/VLM_OCR_QA확인_결과_20261104.md`의 "26.4초, 25초 제한 24/62"(요약과 5절 4번)는 기존 엔진 설정의 값입니다. 결론으로 인용하지 않습니다.
- `vlm_ocr/OCR_비교실험_전체요약_Claude인계_20261027.md`의 "5단계 첫 본 학습은 미시작"은 사실이 아닙니다.

## 7. 사용자가 원하는 작업 방식

- 사용자에게 보이는 모든 글은 한국어 존댓말로, 결론부터 짧게 씁니다. 중간 진행 문장도 포함합니다. 파일명과 코드만 영어로 둡니다.
- 커밋과 푸시는 요청받을 때만 합니다. 이번 작업 파일만 경로를 지정하고, 메시지는 `실험: ...` 형식의 한국어로, AI 공동작성자 줄 없이 씁니다. `--no-verify`를 쓰지 않습니다.
- 다음 단계로 넘어갈 때도 사용자 요청을 받습니다.
- 결과 문서는 요청받을 때만 새로 만듭니다.
- **Google Vision을 사용자 확인 없이 호출하지 않습니다.** 설치도 승인받고, 기존 가상환경의 버전을 확인 없이 올리지 않습니다.
- 사용량이 빠듯하니 오래 걸리는 실행은 백그라운드로 돌리고 지켜보지 않습니다.
- 서비스 시간 제한은 원본 10초, OCR 전체 25초, 앱 35초로 고정입니다.
